== Postmortem: mesh partition outage 2026-10-24 ==

Summary: a mesh routing partition isolated eleven edge nodes for 47 minutes. Client traffic shifted to the fallback gateway with elevated latency but no hard downtime for the control plane.

Timeline: at 14:02 the monitoring alert fired for ring canary packet loss. At 14:05 the on-call acknowledged and started the rolling restart playbook. At 14:11 a second alert confirmed the partition had spread to ring stable. Between 14:15 and 14:40 the on-call captured routing tables, compared ring membership checksums, isolated the misconfigured node edge-17, drained it from the mesh, verified convergence node by node, and restored full routing at 14:49. The long diagnostic window was mostly spent confirming that the fallback gateway was not itself dropping health checks, which required packet captures on three separate nodes and a careful comparison of sequence numbers across the partition boundary. At 14:18 the incident lead opened a parallel track to quantify client impact, pulling fallback gateway latency percentiles from the previous thirty minutes and comparing them against the same window from the day before. The comparison showed p95 latency up from 410 milliseconds to 890 milliseconds on the affected edge segments but zero hard errors on the control plane, which confirmed the fallback path was carrying traffic correctly and bought the team time to diagnose without rushing into a premature mesh-wide restart. That decision mattered later: an early mesh-wide restart would have flushed the very routing tables that ended up proving the root cause. The team also documented intermediate state every five minutes in the incident channel, including which nodes had been reached, which captures were complete, and which theories remained open, so that the post-incident reconstruction would not depend on memory. Between 14:20 and 14:35 the second on-call engineer replayed the interrupted rollout sequence on a spare node and confirmed the mixed-generation behavior could only occur when a power interruption hit between the ring membership write and the configuration generation commit. This reproduction ruled out two alternative theories: first, that the mesh controller itself had broadcast a corrupt membership table, since the controller's own generation log was clean and monotonic throughout the window; and second, that a ring-wide clock skew had caused members to reject each other's sequence numbers, since every captured packet carried timestamps well within the normal drift envelope. Each of these eliminations took time because the evidence had to be gathered node by node rather than centrally, and the partition made direct access to four of the eleven isolated nodes impossible until partial convergence was restored. During this window the team also ruled out a certificate expiry red herring, because the fallback gateway certificate had been rotated the day before and initially looked suspicious. In the end the captures showed clean TLS handshakes throughout, which is what allowed the team to focus on the routing tables and find the stale ring membership entry that edge-17 had been broadcasting since the previous night's incomplete rollout. That rollout had been interrupted by a power blip in the edge cabinet, leaving edge-17 with a mixed configuration generation that the rest of the ring could not reconcile.

Root cause: a stale ring membership entry broadcast by node edge-17 after an interrupted rollout. The fix actually applied: edge-17 was drained, reimaged, and rejoined. The proposed fix of enforcing automatic generation pinning mesh-wide was rejected for now because it would block emergency manual rollouts.
