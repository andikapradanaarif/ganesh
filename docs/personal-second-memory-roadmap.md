# Ganesh roadmap and implementation proposal

Ganesh gives the owner's agents a shared view of work across laptops, servers and authorized projects. A fresh agent should be able to answer two questions from a short, source-linked brief: **“Where did we leave this work?”** and **“How did we handle a similar problem elsewhere?”** The owner chooses which installations and projects may contribute and receive information. Ordinary handoffs should require neither a new summary from the owner nor credentials for another project's repository.

**First product demonstration.** An agent on a laptop leaves a checkpoint in Project A. A fresh agent on a server, working on A, retrieves the last verified action, blocker and next step. Later, while working on Project B, an agent receives one permitted lesson from A, including its applicability limits. The source repository stays private. When A corrects the lesson or the owner revokes sharing, the next server read reflects the change.

**Current stage.** Planned. First measure whether Ganesh returns sufficient, current, authorized evidence through its normal read path. The earlier S0 evaluation ended incomplete at 0/108 formal held-out answers. Its protocol, research and conditional engineering designs are preserved in the [historical roadmap](https://github.com/andikapradanaarif/ganesh/blob/2fddc9d2abfe288e85b9f5f5dceedc20d89ef27f/docs/personal-second-memory-roadmap.md).

**Recommendation for review.** Start with a server that can answer a question by returning an exact passage from a frozen public article. Add source revisions and permissions, then connect the laptop and server. This order lets us locate a failure in retrieval, upkeep, delivery or agent use. A hosted memory product that passes the same workflow with less operational work would also satisfy the goal. The proposed first investment is M1. M2 and M3 each have their own demonstration before expansion.

**Implementation language.** The owner selected Rust for Ganesh. Use Rust and Cargo for the service core, REST and MCP adapters, local capture, importer, developer tools and offline benchmark harness. This decision supersedes the earlier language choice in the historical roadmap and working instructions.

**Start here in a fresh session.** Sections 1–3 describe the workflows, evidence contract and owner controls. Section 4 gives the research and retrieval evaluation method. Sections 5–7 cover milestones, component reuse, implementation and benchmark targets. [Section 8](#8-instruction-for-the-implementing-agent) gives the first implementation task and required report. The targets are proposed, and the current milestone is planned.

## 1. The information an agent needs

| Question | Useful response | Evidence boundary |
| --- | --- | --- |
| Where did we leave this work? | Objective, completed work, last verified action, blocker, next step, producing installation and observation time. Omit unknown fields. | A local test result establishes what ran on that workspace and revision. A proposed next step remains a proposal. A local commit alone cannot establish deployment. |
| What can I reuse from another project? | A self-contained lesson explaining the problem, what was tried, what happened, where it applies and what the receiving agent should check locally. | A standing sharing rule covers the specific published material, its audience and processor. Keep agent-reported reasoning labelled. Preserve the distinction between a reported outcome and an independently checked fact. |

Capture a checkpoint locally when work reaches a meaningful boundary. Give it a stable event identity so the installation can retry delivery. Distinguish captured locally, accepted by the service and available to the reader. If two installations report incompatible work in progress, keep their source and revision visible. A late upload from an offline laptop must not silently replace a newer verified checkpoint.

## 2. One evidence contract for REST and MCP

Use a small server-hosted Rust core with shared retrieval, revision and access logic. REST clients call it directly. Initially, an MCP-capable agent can use a thin local MCP bridge to the same REST service. Add a hosted remote MCP adapter when a selected client needs it. Local capture is a separate adapter at the source installation.

A read supplies the authenticated installation identity, active project, question and optional effective time. The service derives the permitted audience from the credential and policy. Choosing a different project in a request cannot expand access.

Return ranked evidence passages. Each carries a stable item ID, revision ID, scope, provenance label, applicable time when known, and a citation the recipient is allowed to see. Return a short checkpoint or a permitted lesson where it suffices. Project B may see a safe published citation and lesson text while only A can resolve the underlying private evidence. Use one access decision for passages, citations and any derived brief. Exclude restricted information before it can reach a consumer or an unapproved processor.

Return an explicit **insufficient context** result when the permitted evidence cannot support the requested fact. Return **conflicting evidence** with the permitted alternatives when neither supersedes the other. An empty response for B must not reveal the existence, title or path of a hidden source in A.

## 3. How current and historical reads work

**Episodes and semantic facts.** An episode records a particular event, who observed it, when it happened (if known) and its evidence. A semantic fact records what currently applies to a user or project, its scope, effective interval and supporting episode or source revisions. Record ingestion time separately for both. For example, on June 3 the owner says “Starting July 1, use ISO dates in new internal reports.” The episode occurred June 3 even if a laptop uploads it June 5. The preference takes effect July 1 and applies to new internal reports only. A later exception for one project gets its own scoped revision. One observed formatting choice alone cannot establish a general preference.

- **Identity and time.** Give each fact, decision or lesson a stable identity. Record immutable revision identities, source anchors, effective dates when supplied, and observation and ingestion times. Default reads ask what applies now. An as-of read asks what applied on the requested date according to evidence currently available and currently permitted. Unknown effective dates stay unknown.
- **Corrections.** Add a revision linked to the one it supersedes. Publish it and retire the old current view together. Supersession follows evidence, authority and scope. The last item downloaded does not automatically win.
- **Partial corrections.** Suppose the earlier rule required manual approval for staging and production. A correction makes staging automatic from June 1 and leaves production manual. A current staging query returns the new rule. A production query still returns manual approval. A May staging query can return the earlier rule with its historical status. Importing the May document again in July changes none of those answers.
- **Related discoveries.** Give a lesson about *why* a rollout failed its own identity and link it to the deployment rule. Similar words or a later timestamp alone do not establish replacement. If an anchor changes, re-evaluate its dependants and withdraw unsupported guidance from current reads.
- **Revocation and deletion.** If A withdraws B's permission, B's next current or historical read must exclude the affected passage and citation, including cached or derived results. Keep independent permitted material available. Deletion must also cover derived copies under the retention policy. The service can control future delivery; a recipient may already have read an earlier response.

### Owner web interface

Capture, publication under standing permissions, and upkeep run unattended. The owner can open the web interface whenever a brief looks wrong or they want to see whether Ganesh helped. Leaving it unopened must never delay eligible memory delivery or turn an unreviewed report into a verified fact.

- **Inspect a memory.** Open the exact revision cited in a brief. Show its source passage where permitted, provenance, effective time, audience and status. A timeline shows who or what created, changed, shared or withdrew it, when, and why. Link each completed change to the affected revision. Apply current access and deletion rules to the timeline as well as the brief.
- **Correct a memory.** From the revision being inspected, edit the claim, narrow its applicability or withdraw it. Commit an owner-attributed revision through the same service that serves REST and MCP. For example, the owner can correct “all deployments are automatic” to “staging only.” Keep the original source attribution distinct from the owner's correction. If the record changed while the page was open, show the newer revision before saving. Stale capture replay cannot silently undo the correction.
- **Evaluate value.** For a selected project and time period, show how many handoffs received a memory, how many have evidence of use, and how many have an observed outcome. Let the owner open an example and follow the delivered revision to the agent action or optional feedback supporting that assessment. If a lesson was delivered ten times and cited twice, display both counts and label usefulness unknown wherever outcome evidence is missing. Feedback is optional.

## 4. How we will test retrieval

**Build a reproducible corpus.** Choose sources permitted for storage and testing. Use a recorded sampling frame and seed for the public articles, and deliberately include near neighbours on the same topic. Freeze the bytes, source identifiers, dates, revisions, permissions and digests. Record genuine corrections where available. Mark synthetic change sequences as fixtures. Tests should replay offline when a live article changes or disappears.

**Write questions independently of ranking.** For each question, specify what would be sufficient evidence, acceptable equivalent passages, revision, effective time, reader scope and expected outcome. Some questions require multiple facts. Include paraphrases, similar but irrelevant passages, partial corrections, late arrivals, historical reads, missing evidence, conflicting sources and denied access. Split development and held-out cases by source family or change sequence before tuning. Keep the held-out answer key outside consumer inputs.

**Score the response directly.** Report the count of answerable questions for which the first three results collectively contain all required evidence, with the denominator and missed passages. Report missing-evidence and conflict decisions separately. For change and access fixtures, compare revision IDs and permitted text through both REST and MCP. List each obsolete current result, restricted disclosure and adapter mismatch individually. Freeze the roster and numerical promotion criteria before inspecting held-out results. Keep reruns after tuning identifiable as development evidence.

**Then exercise the agent.** In one smoke test the agent calls the real tool, receives a permitted passage and cites the returned revision. Record tool delivery and the agent's use separately. The primary retrieval test requires neither a model-generated answer nor an LLM grader.

**Make citations replayable.** For each public corpus revision, keep the publisher, original URL, retrieval date, storage permission and snapshot digest in the manifest. Give each expected passage a locator within that snapshot. During replay, resolve the returned citation to its revision and passage, then check whether the passage supports the requested fact. For example, a link to the correct deployment guide still misses if the cited paragraph describes production and the question asks about staging. For a shared lesson, perform this check against the recipient-visible publication and test source resolution separately under the source owner's permissions.

### Research behind the benchmark

| Research observation | Choice for Ganesh |
| --- | --- |
| KILT grounds tasks in a common Wikipedia snapshot and evaluates the provenance models return alongside downstream performance. [Petroni et al., KILT](https://aclanthology.org/2021.naacl-main.200/) | In M1, pin the corpus and score whether the retrieved passages supply the required evidence. The top-three cutoff is a Ganesh design choice. |
| Mem0 extracts compact memories from conversations. On LoCoMo, Table 2 reports lower latency for Mem0 and a higher judge score for full context. [Chhikara et al., Mem0, Table 2](https://arxiv.org/html/2504.19413v1) | If M1 misses a paraphrase or a needed qualifier, compare a pinned Mem0 extractor with the original passage baseline on the same question. Check that the extracted claim resolves to a sufficient source passage. Measure ingestion cost, retrieval latency and bytes returned alongside evidence coverage. |
| Zep's temporal graph links facts to episodes and records when a fact applied and when the system learned or invalidated it. [Rasmussen et al., Zep, §§2.1–2.2](https://arxiv.org/html/2501.13956v1) | In M2, ingest an older episode after a correction. Query both before and after the correction's effective date. Verify the returned revision and citation, the unaffected scope, and the owner's correction history. If the baseline struggles with this case, evaluate a pinned [Graphiti implementation](https://github.com/getzep/graphiti) against the same fixture. |
| LongMemEval treats temporal reasoning, knowledge updates and abstention as distinct memory abilities. [Wu et al., LongMemEval](https://arxiv.org/abs/2410.10813v2) | Give the same fact a current question, an as-of question and a question the sources cannot settle. Report the outcomes separately so a good average cannot hide stale responses. |
| TransMem makes transitions between user preferences retrievable. [Chen et al., TransMem](https://arxiv.org/abs/2611.10683v1) | Adapt that question to project evidence in M2: after a partial correction, can the caller find which part changed, when it changed and which part still applies? The Ganesh fixture supplies the expected revisions. |
| MemDev-Bench observed failures when code agents applied earlier experience without checking whether it fit the current task. [Chen et al., MemDev-Bench](https://arxiv.org/abs/2610.27524v1) | In the M3 handoff, check that the published lesson carries the condition the receiving agent needs to verify locally. Record delivery and actual use as separate observations. |
| Recuris uses working memory to track progress and select an applicable skill from past experience during a long task. [Zhaochen Yu et al., Recuris, §§2.1–2.2](https://arxiv.org/html/2608.24876v1) | Give the M3 handoff fixture two permitted lessons on the same topic: one for diagnosis and one for recovery. Change the checkpoint from “cause unknown” to “cause verified” and check which lesson ranks first at each step. |
| Self-Improvement Memory records why a harness edit was tried, its predicted and observed outcomes, and the evaluation conditions so a later optimizer can reuse that experience. [Xin Yu et al., Self-Improvement Memory](https://arxiv.org/abs/2611.18856v1) | For “How did we handle this elsewhere?”, check that the shared passage explains what was tried and under which conditions it worked. Include a case where a proposed fix was never tested: the citation should support a proposal, and the outcome should remain unknown. |

The [earlier research catalog](https://github.com/andikapradanaarif/ganesh/blob/2fddc9d2abfe288e85b9f5f5dceedc20d89ef27f/docs/personal-second-memory-roadmap.md#appendix-f-research-basis-and-implementation-commitments) preserves the broader readings and their limitations. Ganesh's permission and revocation requirements come from the owner's sharing boundary and require direct local tests.

## 5. Delivery milestones

| Milestone | Build | Evidence required to finish |
| --- | --- | --- |
| M1 · Evidence retrieval from a fixed corpus | Import frozen public passages and revision metadata. Implement the shared query function, REST read and thin MCP bridge. Start with the simplest ranking method that can be replayed. | A repeatable offline run over a frozen roster returns sufficient passages, citations and explicit insufficient-context outcomes. Both adapters agree. Publish counts, failures and the predeclared pass bar. |
| M2 · Updates and scoped sharing | Add supersession, historical reads, a permitted publication from A to B, revocation and invalidation of dependent views. | On a two-project fixture, every correction, partial correction, conflict, late-arrival and historical case returns the expected revision or status. B can read the permitted lesson. Denied and revoked reads expose zero restricted passages or metadata, including after restart and through cached views. |
| M3 · Automatic handoff between installations | Connect one selected agent client on one local machine and one server. Capture permitted checkpoints and lessons during ordinary work and deliver a brief on resume or query. | Run the first product demonstration above. Record the source event, revision accepted, actual content served, receiving agent's next action, changes after correction or revocation, and any owner intervention. An owner-written summary cannot fill a capture gap. |

The owner chooses the two installations, client, permitted projects, sharing rule and processor permissions before real enrollment. M1 can start with frozen public material. Record retrieval latency, storage and model use where applicable. Adopt richer ranking, extraction or storage only after a measured failure justifies the change.

**Reuse decision.** EverOS already extracts episodes, atomic facts and user profiles. Letta offers persistent agent memory and blocks that multiple agents can share. Try a pinned candidate against the same public fixtures before writing equivalent extraction or retrieval code. Evaluate direct use first, then the smallest adapter needed for the Rust service. Record passage-level citations, current and as-of answers, behavior after an owner correction, scoped sharing and revocation across installations. Report deployment and processor requirements alongside gaps. If a candidate satisfies the workflow directly, adopt it. **What the repository implementations contribute.** These observations come from source inspection at the linked commits. Adapter compatibility and retrieval quality still require local fixtures.

- **Mem0.** The SQLite history records old and new memory text, the event and timestamps. The open-source `Memory.search` rejects `reference_date`. Use the history view as a reference for showing an owner what changed. If a paraphrase defeats M1 passage search, test whether Mem0's extracted fact retrieves the exact permitted passage with its qualifier intact. Keep effective-date selection in the Ganesh core. - **Zep.** The public repository contains Cloud integrations and examples. Its example agent can search for context and request details by handle. Use that interaction to test whether a receiving agent can open the permitted revision behind a search hit. The public example supplies no evidence about enforcement inside the hosted service. [Repository scope](https://github.com/getzep/zep/blob/5e9f35d7c7dcc7eb1d92f180d9296f39a8c64de8/README.md#L26-L41) · [Example tools](https://github.com/getzep/zep/blob/5e9f35d7c7dcc7eb1d92f180d9296f39a8c64de8/examples/python/agent-with-zep/agent_with_zep/tools.py#L313)

**Web acceptance.** In M2, open a delivered revision in the owner web interface, inspect its source, correct its scope and verify the next REST and MCP reads reflect that correction. Replay the older capture and check the audit timeline and current result. In M3, complete a handoff and an automatic source-driven update while the owner stays signed out. ### First bounded implementation issue

**Implement a reproducible passage lookup from a frozen public corpus (M1).** The deliverable is a Rust importer and retrieval core with a REST read, a thin MCP read over the same core, and an offline evaluation command. Use a small corpus with overlapping subjects, at least one paraphrased lookup and one question the sources cannot answer. Version the corpus manifest and safe fixtures. Document the question split, top-three evidence criterion, numerical pass bar and validation command before running the held-out check.

Acceptance requires (1) a clean offline replay from pinned inputs, (2) the expected passage and revision through both adapters for the known lookup, (3) an explicit insufficient-context result for the missing fact, and (4) a held-out report that meets the frozen pass bar and exposes every miss. Product enrollment, live model grading and a hosted MCP service fall outside this issue. A failed retrieval check gives the next change a concrete target.

## 6. Proposed implementation

### A read that can be explained

Use one small Rust service with SQLite as the proposed first store. Store source revisions, passage locators and their text together. Start with paragraph or section boundaries, preserve headings and qualifiers, and rank permitted passages with lexical search such as SQLite FTS5/BM25. Use a stable passage ID to break ties. Keep the search index rebuildable from the accepted revisions. These choices give M1 an offline baseline that a contributor can inspect and rerun.

| Operation | Proposed behavior |
| --- | --- |
| Import a source revision | Verify the snapshot digest. In one transaction, record the revision and its passages and make them searchable. Reimporting the same source revision and digest is idempotent. A reused revision identifier with different bytes is an error. |
| Search | REST `POST /v1/search` and MCP `search_context` invoke the same function. Resolve the caller and allowed project, select eligible revisions for the effective time, rank the passages and return up to three. Calibrate any minimum relevance threshold on development questions. |
| Open a citation | REST and MCP can resolve the opaque citation to the same revision and passage. Check current permission again when opening it. The returned locator still identifies the frozen passage after the search index is rebuilt. |
| Change or withdraw a claim | Write a linked revision, its support changes and an audit event in one transaction. Use the revision the editor opened as the precondition for an edit. Exclude ineligible revisions immediately on reads, even when rebuilding a derived index takes longer. |

For example, take the fixture question “Did staging still need manual approval on June 10?” The expected hit is the **staging** paragraph of the revision effective June 1. It must include the environment, the rule and the date, or provide permitted passages that establish all three together. A newer article about production may match every keyword and still fail. The API returns the passages and citations so the calling agent can construct its own answer.

### What Ganesh stores and who can see it

| Record | Contents and purpose |
| --- | --- |
| Source revision and passage | Source identity, publisher or producing installation, digest, locator, scope and provenance. Public fixtures can retain permitted source bytes. A private source can remain at its installation with only the authorized excerpt or verifiable reference accepted by the server. Record whether the original can be resolved. |
| Episode | A dated observation, such as a test run or an owner's stated decision, linked to its evidence. Preserve occurrence, observation and ingestion time when known. |
| Fact, checkpoint or lesson revision | A stable item with one or more revisions. Record the claim, project or user scope, applicability, effective interval, supporting revisions, and links to revisions it corrects. A reusable lesson also records what was tried, what happened and the condition the receiving agent must check. |
| Publication and audit event | A recipient-visible revision with its own permitted wording and citation. Keep private support links on the source side. Record who or what published, corrected, withdrew or revoked the revision and why. Enforce the same access rules when displaying audit history. |

**Sharing example.** A private report in A says a generated client had to be regenerated after a schema change. A standing rule allows B to receive a lesson about generated clients. Publish the procedure, the observed result and the condition “only if this client is generated from that schema.” B opens the published passage. A's file path, repository URL and transcript stay on A's side. If A later corrects the condition, the maintained publication must either cite the corrected support or disappear from current reads. This also applies to a brief prepared before the change.

**Automatic capture and upkeep.** In M3, use one selected client's permitted event to trigger capture of a checkpoint or lesson candidate. Persist its event ID locally before attempting delivery and acknowledge it only after durable service acceptance. Check source support and the standing publication rule before making it visible to another project. On a new source revision, find dependent claims and re-evaluate their support. A missing or changed anchor can justify withdrawal. A read or network error leaves the cause unresolved and triggers a later check. Record verification status so callers can distinguish the last verified observation from a new assertion. Replay an offline event and restart the service during the demonstration.

### Which existing components earn an integration

The first comparison uses the same inputs, eligible passages, questions and citation resolver for each candidate. Grant a processor access only to material approved for that processor. Record the exact version, dependencies, external calls, storage, latency and any custom adapter code. Select the smallest deployment that meets the tested workflow.

| Observed need | First comparison | Decision |
| --- | --- | --- |
| A paraphrase misses the right passage | Compare lexical retrieval with a semantic or hybrid retriever on the same passages. If compact facts could recover the qualifier, also try the pinned Mem0 extractor. | Adopt the change only if fresh questions show better evidence coverage and citations still resolve. |
| Ordinary work produces useful discoveries but no stable lesson | Try the EverOS episode and atomic-fact extraction path on permitted, scrubbed events. Keep a mapping from each candidate to a source revision. EverOS documents separate source and rebuildable search storage. [EverOS implementation guide](https://github.com/EverMind-AI/EverOS/blob/d2b74780a443c6d7304ca9aa1bfdf36fdc6d7c9b/docs/how-memory-works.md) | Compare qualification, upkeep and operating cost with the simplest source-linked checkpoint. Import additional EverOS components only for a measured need. |
| A receiving agent needs a persistent shared brief | Try a Letta shared block as a delivery surface. Change or revoke its supporting publication and exercise both installations against the same fixture. [Letta shared blocks](https://docs.letta.com/tutorials/attaching-detaching-blocks/) | Reuse the delivery surface if refresh and revocation meet the read contract. |
| Multiple supports and late corrections make historical selection unreliable | Compare the SQLite revision model with pinned Graphiti on the M2 fixture. Use the Zep search-then-open interaction as a client reference. | Adopt a graph adapter only if it fixes the observed failure and passes the same scoped reads, removals and restart checks. |

## 7. Proposed first benchmark and decision rules

**Corpus and questions.** For a first engineering gate, propose 24 answerable held-out questions and six with insufficient evidence, in addition to a separate development set. Sample articles from a recorded list of sources permitting snapshot storage and replay. Record the seed, exclusions, license or permission, bytes and digest. Include near neighbours deliberately. Hold all versions of one article family on one side of the split. Freeze questions, required facts, acceptable passage IDs or equivalents, scopes and revisions before evaluating the held-out set. Keep the key outside the search index and agent inputs. The counts below are proposed acceptance targets for the implementation issue.

| Check | Proposed decision rule |
| --- | --- |
| Sufficient evidence at three results | At least 20 of 24 answerable questions have every required fact supported by their returned top three. A hit on the right article with the wrong paragraph receives zero for that question. Publish each miss and the counts for paraphrases, distractors and multi-passage questions. |
| Insufficient evidence | All six missing-evidence cases return explicit insufficient context. An answerable question that abstains also counts as a miss in the first row. |
| Citation and adapter integrity | Every returned citation resolves to the returned passage and revision for that caller. REST and MCP agree on status and ordered passage IDs for all 30 questions. An unresolved citation or adapter mismatch blocks promotion. |
| Reproducibility and cost | Replay from a clean store, verify snapshot digests, rebuild the index and compare outcomes. Record import and query time with hardware and corpus size, response bytes, storage and provider calls. The proposed lexical baseline runs offline with zero provider calls. |

These numbers are an engineering decision for a small fixture. Report counts with denominators. A pass supports building M2; broader claims about retrieval quality need new sources and questions. On failure, use the missed cases for diagnosis, record which inputs became exposed, and freeze a fresh held-out set before claiming improvement. A partial run is incomplete.

**M2 lifecycle replay.** Run the following in order using an owner in A and a receiving installation in B. Check searches and citation opening after each step, including reads through both adapters after a restart.

1. Import an original rule and publish a permitted lesson. Both callers can cite what they are entitled to see. B can search and open the publication without access to A's repository.
2. Apply a correction effective June 1 for staging only. Ask about May staging, June staging and June production. Record the exact expected revision and scope for each. Upload the older snapshot after the correction and repeat all three reads.
3. Add two equally authoritative, incompatible reports with overlapping scope and no supersession. Expect a conflict with permitted alternatives. Narrow the scope of one report and check the unaffected answers.
4. Give one claim two independent sources. Remove one and check the remaining citation. Then withdraw the only support permitted to B while A retains private support. B gets insufficient context, including on a historical lookup or when opening its old citation. A can still resolve its own support. Check returned text, titles, IDs and cached briefs for leakage.
5. Correct the claim from the owner web interface. Replay the old capture and confirm the correction survives. Verify the audit trail, then exercise source deletion and derived-copy removal under the configured retention policy. Record which references, if any, the policy allows the owner to retain.

**M3 product decision.** A successful handoff needs evidence of automatic capture, a service receipt, the exact revision delivered on a second installation, and the observed next action. Repeat for a cross-project lesson under a standing permission. Change the supporting source with the owner signed out and inspect the next read. If the agent receives the right passage and ignores it, record delivery as successful and use as unobserved or declined according to the trace. Only describe owner time saved or better agent outcomes when separately measured. No historical S0 score or literature benchmark supplies that evidence.

## 8. Instruction for the implementing agent

Once the owner accepts the roadmap, open one M1 implementation issue against the evidence-retrieval milestone. Put the corpus permissions, sampling method, development split, proposed pass counts and exact replay command in the issue before the held-out run. Use Cargo to build the Rust importer, passage search, citation resolver, REST/MCP adapters and offline evaluation command on an issue branch. Keep retrieval, revision selection and access decisions in a shared library so the benchmark exercises the same behavior as the service. Include a known lookup and an insufficient-context case that another developer can replay from a clean checkout.

Open a draft PR with the command, manifest digest, per-question outcomes, adapter comparison and measured costs. If the baseline misses, bring back one concrete failing question, the passage that would have satisfied it, what the service returned and the smallest change worth testing. A passing report earns the M2 fixture. Select the real installations, client and processing permissions with the owner before M3 enrollment.
