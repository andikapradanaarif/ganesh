## 0. Roadmap overview

**The product:** build a personal, evolving memory service for the agents working across the owner's projects. It runs in the cloud, offers both a RESTful API and MCP, and keeps useful context available across authorized tools, agents, sessions and devices.

**The problem:** knowledge accumulates in individual conversations, repositories and tools. A new agent or session often needs the owner to reconstruct the context: what was decided, what was tried, what changed and what another project already learned. Repeated explanation becomes part of every handoff, while useful discoveries remain difficult to reuse.

**The intended experience:** the owner starts work and the agent receives a short, relevant brief. As work progresses, the service captures permitted reports and source changes, updates project memory and makes eligible knowledge available to other authorized agents. When evidence changes, memory can change with it. The owner can inspect where a statement came from and correct, pin, undo or delete it.

**Owner responsibilities:** configure access and retain control. Routine operation must require no manual note-taking, session summaries, per-item approvals or recurring semantic review. The owner may optionally supply preferences, decisions or corrections. Setup, credential renewal and exceptional incident handling remain explicit administrative costs. Neither missing owner feedback nor elapsed time since a review disables otherwise eligible memory. Automated checks, expiry and scoped incident pauses remain mandatory; they do not establish semantic truth.

**The first usable product:** an agent resolves a meaningful problem; the service automatically captures the result and its limitations; a fresh authorized agent correctly reuses it; changed evidence updates or withdraws the memory. Demonstrate this both within a project and across authorized projects without newly written owner summaries. Verified project state supports this cycle but cannot substitute for discoveries, rationale and failed approaches. Existing instructions remain a baseline and optional owner contributions never fill an automatic-capture gap.

Start by testing S1a-lite: generated cards in a private git repository, REST/MCP reads, durable checkpoint/manifest intake and installation control synchronization. A small SQLite intake store is permitted without adopting the full gateway. Build the fuller gateway only when measured requirements justify its additional interfaces and guarantees. The initial conservative origin policy may yield almost no eligible narrative; that is a possible failure of the intended product, not successful delivery of a smaller status service. A2.3 defines a separately budgeted lower-trust experiment if needed; it grants no production exception.

**The longer-term direction:** richer capture and maintenance, reusable discoveries and decisions, and more connected sources. EverMind/EverOS remains a candidate for extraction and later retrieval. We will evaluate reuse early, while keeping ownership of memory and its controls.

**Research direction:** preserve source-linked experiences as well as facts; test useful reuse, correct updates and resistance to poisoned memory. Recent papers inform these choices; the target workload must establish their value.

**The next move:** use [the S0 execution sheet](s0-execution-sheet.md) to start S0 day 1 with the one-hour transcript screen and bounded capture setup. The day-one inventory fills actual project, client and model identifiers; do not invent them or begin held-out runs before budgets/rubrics are frozen. Compare raw tools/native instructions (0) with typed cards (A), with fixed within/cross-project strata and required diagnostics. A1 precommits the mixed-origin routing threshold and the single first-party eligibility recheck. No experiment or hook installation has been run. Part II remains conditional reference material, not the day-one implementation task.

**Success:** less repeated explanation, better continuity between agents, useful memory that stays current, and low owner upkeep. A large memory database or an elaborate audit console alone is not evidence of product value.

## 1. Vision

**Agents should build on knowledge already established by the owner and other authorized agents.** Switching a conversation, repository, tool or device should not mean rebuilding all relevant context from the beginning.

The service becomes a durable memory of the owner's work: important decisions and their reasons, discoveries worth reusing, approaches that failed, current project state and the preferences that genuinely apply. It keeps the source and scope of that knowledge visible, so an agent can distinguish a local report from an established convention or a verified observation.

Memory evolves through new evidence, corrections and changes in the work. The ambition is for the service to maintain that context with little routine attention from the owner. The owner can inspect the service’s changes, understand their basis and intervene directly.

The product serves coding, planning and review across projects. Its purpose is to help the next task begin with useful context and avoid repeating avoidable mistakes. Broader integrations and more sophisticated memory are valuable when they improve that experience.

This is the destination. The first release deliberately tests a narrow part of it; the roadmap must earn the richer capabilities through observed usefulness and reliable operation.

## 2. Problem and intended value

The initial scope is one owner working with multiple agents across multiple projects. The service needs to improve ordinary work often enough to justify its setup and upkeep.

| Situation | Intended improvement |
|---|---|
| A fresh session starts with little project history | A compact brief provides relevant state, decisions and source references. |
| One agent discovers something another project could use | Eligible knowledge becomes available across the permitted projects, with its scope and evidence attached. |
| Yesterday's remembered state becomes wrong | New evidence refreshes it, or the service marks the uncertainty instead of quietly presenting it as current. |
| An automatic update looks suspicious | The owner can trace its inputs, checks and effects, then correct or undo it. |
| Keeping memory organized becomes another job | Routine capture and upkeep run automatically; blocked items do not become an approval backlog. |

The strongest product hypothesis is that continuity and reuse reduce both repeated explanation and repeated work. We will measure those outcomes. Token savings, source coverage and audit completeness help assess the system, but each answers a different question.

Native project instructions remain part of the working environment. The memory service adds evolving, source-linked context across sessions and authorized projects. S0 first compares cards with native instructions and raw tools alone; packaging is secondary, and richer-history diagnostics test the content ceiling. S1a-lite separately tests whether scheduled card generation and git already provide sufficient operation and control.

## 3. What using the product should feel like

**Connect client tools.** An MCP-capable agent uses the MCP interface. A script, application or custom agent can use the RESTful API directly. Both reach the same memory, permissions and available audit history; the owner does not maintain two copies. REST is first-class because hooks, scripts and CI jobs often use ordinary HTTP and do not implement MCP.

**Start a task.** The owner opens a project with a connected agent. It asks for a brief suited to coding, planning or review and receives the permitted context with age, evidence and source references. The owner can continue without preparing another long handoff message.

**Finish or pause work.** The integration captures structured checkpoints automatically and observes enrolled source changes. A local hook reduces/scrubs events into its durable spool; the uploader synchronizes controls and retries delivery, and the service scrubs again. Captured locally, accepted by service and available for reuse are distinct states. Initial client narrative becomes eligible only after session closure and reconciliation; a pause or active-session checkpoint does not promise immediate sharing. Verified observations can update independently. No owner summary or review queue is required.

**Move to another project or device.** The next agent can request the same authorized memory. It should be able to discover a relevant lesson or decision and inspect its conditions and evidence. Verified facts remain one tier. An experimental advisory tier can carry bounded first-party lessons whose references and origin are checked, but whose meaning is not verified. S0b-2 must establish whether that tier provides useful reuse at acceptable residual risk before it enters either first-release design.

**Inspect or intervene when needed.** From a remembered item, the owner can open its source, see what changed and why, and correct, pin, undo, delete or pause. Inspection and semantic feedback are optional during normal operation. The service must not require the owner to keep a review queue or periodically visit the console to sustain useful memory.

For example, suppose an agent learns why a retry strategy failed in project A. The product ambition is for a later agent in project B to reuse that lesson with the relevant conditions and evidence. S0 explicitly compares what typed cards can convey with a free-text reference card. S0b-2 then tests whether a bounded advisory lesson preserves the value. If only unrestricted prose helps, neither verified status fields nor an unproven advisory tier is a successful fulfillment of this example; stop or rescope before infrastructure.

## 4. How memory evolves and how the owner stays in control

The operating cycle is **capture → check → update → share → refresh**.

1. **Capture:** scrub permitted source observations and agent reports before storage, with project attribution and provenance; scrub again before every model dispatch.
2. **Check:** distinguish what was reported from what an appropriate source supports. A model can suggest a memory; it cannot invent permission or make its own confidence into evidence.
3. **Update:** apply eligible changes to the project's working memory. Preserve useful uncertainty, respect the owner's corrections and pins, and avoid overwriting unrelated changes.
4. **Share:** publish qualifying information to an already allowed audience. Verified typed facts and experimental advisory lessons have separate checks and labels. Other unverified reports remain within their originating project.
5. **Refresh:** react to new evidence, corrections and expiry. Keep an older publication only while it remains eligible; withdraw information that is deleted, restricted or no longer supported.

“Evolving” means the retained knowledge and its organization change over time. It does not require retraining a model. The first release handles structured updates; broader extraction and semantic maintenance follow only when their value and error rates justify them.

Owner control has two parts: configure sources, audiences, processors and operating limits; inspect or intervene when desired. Both verified and admitted advisory memory must operate without recurring owner review. Build §10 uses automatic checks and scoped incident responses, with semantic uncertainty reported honestly. Administrative reauthentication or an exceptional integrity incident may require attention; isolate the affected scope. If useful narrative requires routine human review or authorship to remain acceptable, the intended unattended product has failed that requirement and needs an explicit scope decision.

Auditability makes the process inspectable and repairable. It cannot prove every claim true or reverse actions an external agent has already taken. Evidence checks and limited sharing therefore remain part of automatic operation.

### 4.1 Research behind the product

**The research supports testing a memory that learns from work, updates with evidence and helps the next task. It does not establish that a larger memory store will always help.** Appendix F records the primary sources, the claims they support and the limits of that evidence. The selected reading emphasizes 2026 work and retains Mem0's 2025 foundation; this is a focused review, not an exhaustive survey.

| Research direction | Roadmap implication |
|---|---|
| Structured episodes and compact memory — EverMemOS and Mem0 [Q1, Q3] | Keep source-linked observations distinct from extracted claims; test a reusable extractor before building our own. |
| Learning reusable procedures — ReMe [Q2] | Test lessons that retain conditions, attempted action and observed outcome. A useful lesson needs more than an isolated fact. |
| Experienced-agent evaluation — LongMemEval-V2 and EvoMemBench [Q4, Q5] | Test state, workflows and transfer; compare an agent searching raw scrubbed session summaries and a mandatory full-context diagnostic before retrieval machinery. |

**Initial commitments:** source-linked records, separate working and published memory, lane-specific automatic checks, bounded updates, secret scrubbing, owner controls, and tests covering both useful recall and harmful reuse. These are our design choices informed by the research, not guarantees supplied by a paper.

**Next experiments:** S0b-1 tests deterministic verifiers, origin restrictions, scrubbing and repair. A1 defines the exact first-party gate and failure path: M/H ≥50% routes immediately to the separately budgeted A2.3 decision; otherwise the single final recheck must meet all six-lesson, two-project, E/H ≥50% and six-applicable-task requirements. A failed recheck follows that same A2.3 decision, even when some lessons are eligible. S0b-2 tests one extractor and only the narrative path that earned its gate, comparing bounded lessons with facts-only and free-text references. Reference/origin checks do not verify meaning; residual risk and unattended usefulness remain separate gates. No production narrative lane is enabled by a routing decision.

**Conditional capabilities:** richer consolidation, adaptive retrieval and experience-based maintenance. EverMind/EverOS remains the first extraction candidate where suitable; mem0 is an alternative. Graph storage, a new memory engine and a fork are not prerequisites. Appendix F gives the exact readings, limitations, stage mapping and acceptance evidence.

## 5. Goals and the first release

The primary goals are continuity across sessions and devices, useful knowledge reuse across authorized projects, automatic upkeep, and owner control with a clear source trail. The minimum product outcome includes automatically captured discoveries and their limitations, not only current project status. Owner-provided preferences, decisions and corrections are optional supplements. Repository ownership or a signed commit does not establish authorship; changing the product goal does not relax provenance or disclosure rules. A typed-only or own-project-only service is a separately chosen reduced scope, not fulfillment of the complete product goal.

| First release includes | Expected capability |
|---|---|
| A few personal projects in one explicit sharing group | Choose where memory is collected and shared. |
| RESTful API and MCP over one service, one agent integration and one read-only source connector | Connect an agent or ordinary HTTP client and check a handoff between two installations. |
| Project working cards and separate published tiers | Share verified typed facts; include advisory lessons only after the prebuild gate passes, visibly labelled as unverified meaning. |
| Short briefs and automatic knowledge upkeep | Capture and reuse useful discoveries without owner summaries; update or withdraw them when supporting evidence changes. |
| Inspectable history and owner controls | Follow a change, correct, pin, undo, delete or pause. Lite first uses git and a control file; a console belongs to the conditional gateway build. |
| Recoverable, portable memory | Recover from the declared failures and export owned data. |

The shared choices are cloud access for continuity, REST and MCP over one policy boundary, automatic lane-specific checks and direct owner controls. Lite keeps cards in private git and may use SQLite for transactional intake, receipts and work queues. Storage technology does not define the gateway boundary: the fuller service adds its declared write, concurrency, audit and recovery guarantees. Part II specifies that conditional gateway; passing a token or typed-status pilot alone does not authorize its build.

EverMind/EverOS stays in the plan as an early extraction candidate. A successful component can be reused without handing it ownership of the whole product. Adoption, a wider retrieval role and any fork require evidence that they solve a demonstrated need.

Broader source coverage, richer semantic memory and restricted employer/client projects are later work. Task scheduling, repository locking and external actions such as sending messages or changing source systems are outside this release.

**Benchmark and fork priority.** S0 through S1a prioritize the local automatic discovery-to-reuse case. High LoCoMo-style scores and leaderboard placement are explicitly deferred research goals; these stages neither measure nor claim them. No separate benchmark track or mem0/EverOS fork is funded by this plan. Before any later benchmark effort, separately freeze dataset/split, baseline/model/judge, cost and contamination controls. Prefer a wrapper or reusable extractor before a fork, and require a measured limitation to justify one. Deferral is a roadmap priority, not evidence that benchmark performance is unimportant or already achieved.

## 7. Success and next decision

Evaluate the product using five questions:

- Does the owner explain less when starting or handing off work?
- Do agents reuse relevant knowledge correctly across permitted projects?
- Does memory stay useful as the underlying work changes?
- Can useful automatic memory keep operating without owner-written summaries or recurring semantic review?
- Can the owner understand and repair a bad memory at acceptable cost?

The immediate action is S0 day 1 using selected personal projects and their real transcripts; synthetic material remains useful for safety fixtures. Start hook capture alongside task preparation, then run only the S0b work justified by those results. Before their held-out runs, fix the tasks, source predicates, budgets and stop rules. Appendix A contains the execution protocol.

**Mandatory product acceptance case.** Agent A encounters and resolves a meaningful problem in ordinary authorized work. With no owner-authored summary or item approval, capture and extraction retain the discovery, relevant evidence, uncertainty and applicability limits. A fresh agent B with no inherited conversation retrieves and correctly applies it on a genuinely dependent task. A later evidence change causes automatic revision or withdrawal, and a fresh consumer avoids invalidated reuse. Test within-project continuity and cross-project reuse separately; status-only fields cannot satisfy either case. Freeze the expected outcomes and score independently in A2.2.

Proceed to the intended-product lite trial only when this case and the relevant safety gates pass. Pilot evidence earns a bounded trial, not general semantic assurance. Typed-only gains, cross-project access gains, optional owner contributions and hand-authored reference cards have separate accounting. If the conservative policy excludes essential knowledge, use the separately budgeted A2.3 experiment or stop; choosing a status-only or own-project-only service is an explicit change of product scope. Proceed to a gateway spike only after a reproducible material lite failure remains unsuitable for a bounded repair.

**Product direction:** personal cloud memory that grows with the owner's work, helps the owner's agents reuse what has been learned, and remains inspectable and controllable by the owner without making the owner its routine reviewer.

## Part II. Conditional S1a gateway build specification

Apply this contract only after Appendix A selects the gateway over S1a-lite. Lite uses A3's simpler credential profile and may use embedded SQLite intake without selecting this gateway. The intended product requires automatic discovery-to-reuse under §7; typed state and optional owner contributions cannot substitute. Client narrative remains disabled until Build §4.1's provenance/capture gates pass, including own-project briefs. Build §6.1's first-party advisory contract needs S0b-2 evidence and a standing configuration choice; there is no recurring owner-review requirement. A2.3 is a separate lower-trust experiment and grants no production exception. An explicitly chosen reduced scope must be labelled as such.

### Build §1. Release boundary and topology

S1a serves enrolled personal/synthetic projects whose data may enter the selected cloud deployment and share one configured processing policy and disclosure group. Enrollment is an owner administrative action. Employer/client projects, differently restricted sources, source-device-only data, arbitrary raw cross-project reads and external-system mutation are disabled. A readable credential alone does not authorize intake or disclosure.

Deploy one authenticated service with **REST and MCP adapters over the same application core**, bounded background workers, one SQLite database on durable host/block storage, one read-only source connector, a small owner console and separate backup/secret storage. The first source connector may use MCP or the source's documented HTTP API; select one in the spike. An incoming REST API does not authorize arbitrary outgoing HTTP access. Workers submit changes through the core. Throughout this specification, “gateway” means this shared service boundary, not only its MCP adapter. Only the gateway commits canonical memory, policy, jobs and audit state. Do not deploy shared WAL files across network filesystems or multiple active writers [R6].

One source connector can serve multiple explicitly enrolled repositories/projects within its account scope, using suitable read-only credentials. Start with structured agent reports, exact source mappings and the narrow automatic extraction path proven by the product case. Reusing an existing extractor is optional; automatically preserving useful discoveries is required for the intended product. Deterministic status mappings alone do not meet it. General transcript coverage, a reflection engine and an arbitrary graph are not required for this narrow supported profile.

The complete gateway surfaces are sessions/checkpoints, installation control synchronization, own-project reports/working cards, published bundles with explicit lanes, deterministic briefs, source synchronization, owner controls, audit, export and tested recovery. General semantic search, portfolio scoring, historical `known_at` queries, replay of arbitrary offline agent actions, entity cards and external action tools are outside this release. Bounded capture-spool catch-up remains required and always rechecks current controls.

### Build §2. REST, MCP, application identity and credentials

**Two public interfaces.** Provide versioned JSON resources under `/v1` over HTTPS and an MCP interface. Both call the same application operations, permission checks, source verifiers, transaction functions and audit pipeline. REST is usable without an MCP client: hooks, scripts and CI jobs often cannot speak MCP, so their integrations must not depend on an MCP runtime. No adapter or console writes SQLite directly, and no interface is a shortcut around publication rules. Generate OpenAPI resource schemas and MCP tool input/output schemas from the same versioned domain-schema definitions; never maintain two independent copies. Publish the OpenAPI contract with authentication requirements, examples and errors; use a pinned supported OpenAPI version [R14–R16]. The public API version is independent of the MCP protocol revision and this roadmap.

**MCP protocol contract.** Target MCP **2026-07-28** over authenticated HTTPS. Requests declare the protocol version and capabilities; implement discovery and validate the selected revision with a pinned SDK. Use a tested compatibility adapter for **2025-11-25** clients/servers. Modern and legacy lifecycles differ: do not negotiate a modern lifecycle merely by returning a modern string in a legacy initialization response. Unsupported versions fail explicitly [R1–R3].

The service does not depend on protocol-level sessions, Roots, Sampling or Logging. Deprecated features are not the same as universally removed features. Models use configured provider APIs; application audit is independent of MCP logging [R1]. Validate HTTP metadata against the request body, enforce private/no-store caching for protected content, and contract-test reconnect/retry behavior [R2]. A transport retry has a new wire request ID but retains the application idempotency key for the same logical write. Test complete result envelopes, discovery and version-error behavior against the pinned SDK; an authorization failure or network outage must not silently select weaker authentication or a legacy fallback.

`sessions.open(project_id, client_session_id, idempotency_key)` over MCP, or `POST /v1/sessions` over REST, authenticates the installation, validates its grant and returns the same kind of server-minted `app_session_id`. REST session-bound calls carry it in the application-defined `X-App-Session-ID` header; MCP carries it in tool arguments. Where a resource path also names the session/project, both bindings must match. The header is our application contract, not an MCP standard header. Every session-bound call supplies that handle explicitly, including `remember`, `propose_card`, `brief`, `get` and `sessions.close`. Portable intake and installation controls are explicit exceptions: `POST /v1/checkpoints` and `POST /v1/manifests` accept an optional `app_session_id` and require project plus stable `client_session_id`; installation control synchronization uses its installation-bound grant under Build §11. Neither exception grants session-scoped memory read or patch capabilities. If a handle is supplied, validate it and any header/body binding; a mismatch never falls back to sessionless intake. A handle is not a bearer credential: every call independently authenticates and checks actor, installation, owner, project, capability, expiry and revocation. Owner commands use an owner administrative context; source jobs carry explicit connector/job/project binding. No operation guesses a project from the last request or an active transport connection.

The registry uses normalized repository identity and component-safe workspace mappings. Ambiguous sessions get at most three automatic resolution attempts when registry/evidence changes, then become `unattributed`. They expire after seven days without writing to a guessed project. No owner response is needed. Denied/unattributed requests retain only the minimum policy-permitted payload; do not upload otherwise unauthorized bytes just to diagnose attribution.

**Separate credentials.** Inbound service tokens and outbound source tokens are distinct. REST and MCP credentials resolve to the same stable owner/client identity and capability model; the selected token audience must authorize the interface being called. An interface switch cannot expand authority. Check issuer, intended audience, scopes and current grants; never pass an incoming memory-service token to an upstream service. Bind stored OAuth credentials to the issuing authorization server, validate issuer identification when supplied, and reject unconfigured discovery/redirect destinations. Pin the SDK's authorization behavior and test the current specification requirements [R4–R5]. Application handles cannot broaden token scopes.

**Gateway credential contract by client class.** These are conditional gateway choices, not lite prerequisites or assertions that all MCP hosts support every credential type. Authorization-server selection, hosting/configuration and client integration are explicit spike/build work; no existing personal authorization service is assumed. A3 compares simpler lite options.

| Client class | Inbound credential and lifecycle |
|---|---|
| Interactive MCP agent over HTTPS | Follow the selected MCP authorization flow using the configured authorization server, discovery, resource-bound OAuth access tokens and supported refresh/registration behavior [R4–R5]. Never silently fall back to a machine token on auth failure. |
| Hooks, scripts and CI over REST | Owner-enrolled per-installation key pair and fixed project/operation grant; installation cleanup uses its separately scoped Build §11 grant. A maintained authorization service authenticates the installation with `private_key_jwt` and issues a proof-of-possession-bound access token lasting at most one hour [R17–R18]. No separate long-lived bearer renewal token. The enrolled key/grant has a hard 180-day authorization expiry; see the lifecycle below. |
| Owner console and owner CLI | Owner login/OAuth administrative credential with a separate audience/scope from agent tokens. No embedded owner credential in hooks, extractor workers or ordinary agents. |
| Internal workers and source connectors | Workload identity plus explicit job/project binding for the core; separate provider-issued read-only credentials for outbound fetches. Neither is an inbound MCP/REST user token. |

**Machine-key lifecycle.** The installation key is the real durable credential; it is not hidden behind the word “renewal.” Bind its public-key thumbprint to owner, stable installation ID, permitted projects/operations and exact token-service audience. Prefer a non-exportable key in an OS/hardware keystore, accessed by the hook/signing process rather than injected into the agent's environment. Store no private key on the service. Use a maintained implementation of JWT client authentication [R18] and DPoP sender constraint [R17]; DPoP alone is not client authentication. Short-lived client assertions require audience/expiry/replay checks, and resource requests require the token's bound key, request-specific proof and server nonce/replay checks. TLS and ordinary authorization checks remain required.

The owner-enrolled authorization expires after **180 days**, and token expiry cannot extend beyond it. An installation may roll its key automatically within that authorization using proof by both old and new keys, with at most 24-hour overlap; rolling keys cannot extend the authorization's original end date. Extending that date or recovering a lost key needs authenticated owner re-enrollment. Revocation disables the grant and all its tokens immediately at the service boundary. There is no renewal-only bearer credential and no silent fallback to one. Count authorization-service provisioning/integration, key storage and lifecycle tests in the conditional gateway budget. Lite uses its explicit A3 bearer-key profile, with a different theft/replay risk; this is not an automatic gateway fallback. Unsupported clients are excluded or require an explicitly revised credential contract.

Map all token/key generations to the same stable client identity so rotation preserves idempotency. Machines cannot widen grants or mint owner privileges. Issuance, rotation, expiry and revocation are audited without values. Interactive MCP clients retain the selected MCP authorization flow; do not assume every host supports this machine path.

**Same-user compromise remains in scope as a residual threat.** An injected agent with shell access under the same OS user can read an environment bearer token or software private key, or invoke an accessible signing helper. It can then submit false reports within that principal's write scope; a valid signature proves possession, not honest authorship. Non-exportability reduces key theft but does not prevent use by a compromised process that can call the signer. Enforce narrow report-only grants, rate limits, independent verified-field predicates, origin labels and revocation; isolate the hook/key helper where feasible. No claim is made to resist a fully compromised same-user client. Its hook manifests can also be forged, so client-attested lessons retain that trust assumption. Test stolen bearer use, wrong-key proof and same-user signer abuse separately: the first two must be rejected by this profile, while correctly authorized false reports may remain local `reported` data and must never self-certify verified facts.

Store usable OAuth tokens/refresh credentials in a separate encrypted secret store, accessed through workload identity. The database, prompts, logs, diffs and exports contain only opaque secret references. Require **provider-enforced read-only scopes or an equivalent read-only principal**, plus the gateway tool/argument allowlist. The allowlist is not a substitute for provider scopes. Use short-lived access tokens where the provider supports them, automatic refresh and rotation, and revoke access on de-enrollment. If a source cannot meet the release's read-only boundary, exclude it; do not quietly accept a broad token. Provider-imposed lifetimes and renewal limitations must be recorded honestly.

### Build §3. Minimal record model and API

The following are separate canonical objects: project/session, source observation, report/candidate, field revision, working card, publication bundle, file-version provenance/coverage evidence, installation control sequence/purge acknowledgment, job/outbox, policy/rule configuration, retry outcome and audit event. An immutable field revision can later have its body purged; immutable identity does not mean permanent retention of sensitive text.

| Fields | Required meaning |
|---|---|
| Identity | Gateway-assigned IDs, owner/project, actor/client or connector/job, application session (nullable for portable intake, with required stable client session), record time and logical `commit_seq`. |
| Source | Connector/account/object, source revision or canonical content hash, source occurrence/observation time, field/span selector, source trust class and policy version. |
| Claim | Subject, lane, typed value or bounded advisory fields, evidence references, and `reported`, `source_supported` or `owner_asserted`. Advisory text remains `reported` or `owner_asserted`, never `source_supported` merely because its anchors exist. |
| Origin for all narrative | `first_party_only`, `mixed` or `unknown`; basis `server_observed`, `client_attested` or `owner_attested`; root session, manifest/coverage revision, reconciliation status, exact file-version provenance and inherited dependencies. The service derives these from accepted evidence; caller flags alone cannot set them. Advisory records separately carry `anchors_checked`, never semantic verification. |
| Validation | `pending`, `passed`, `failed` or `quarantined`; verifier/version, exact candidate and evidence hashes, result/reason, expiry. |
| Concurrency | Per-field revision/read set, write set, relevant source/rule/policy/pin versions and logical operation identity. |
| Control | Active/retired/redacted lifecycle, owner pin/version, optional challenged/contested marker, dependency links and publication eligibility. |
| Publication | Exact field revision IDs, audience, disclosure-rule version, validation references, publication time, last-supported times and bundle revision. |

`reported` means the agent/source said it. `source_supported` means a verifier established the precise allowed predicate against its cited source. It does not mean the source is infallible. `owner_asserted` records a direct owner assertion; it is neither model-assigned nor automatically sufficient for cross-project publication. Assertion, pin, validation and permission are independent.

The gateway derives protected fields. A caller cannot set its own evidence level, successful validation, owner identity, source trust, policy, pin, audience or processor. Preserve case-sensitive identifiers and the full semantic command when hashing identity. Search normalization, if any, never determines whether a write exists.

| API group | Commands |
|---|---|
| Agent | `sessions.open/close`, `checkpoint`, `manifest.append`, `remember`, `propose_card`, `brief`, `get`. |
| Installation | `controls.sync`, `controls.ack`: authenticated installation-scoped cleanup metadata, no memory content or owner mutation capability. |
| Internal | Source sync, validate, apply eligible patch, publish eligible bundle, expire/retry jobs, retention purge. |
| Owner | `correct`, `pin/unpin`, `undo`, `redact`, `pause/resume`, policy/connector administration, export/restore. |
| Audit | `audit.list`, `audit.trace`, `audit.diff`, `audit.verify`, optional `audit.label_sample`. |

There is no routine `approve`/`confirm` operation. Every read, count, relationship and export is authorized; diagnostic routes are not bypasses. Own-project clients may explicitly inspect permitted reports and working fields with origin labels; mixed/unknown text is excluded from automatic briefs and memory-generation input under Build §4.1. Other projects receive only currently eligible verified fields and, if enabled, separately labelled advisory lessons. Owner audit access remains authenticated and purge-aware.

### Build §3.1 REST resources and interface parity

These routes are the proposed S1a contract, to be captured in OpenAPI during the spike. All protected operations authenticate independently. Agent operations also require Build §2's explicit application session, except session creation, portable checkpoint/manifest intake with explicit project/client-session binding, and installation control synchronization with its separate installation grant; owner routes require owner capability. Internal validation, publication and source-sync operations are not public agent capabilities.

| Resource / HTTP operation | Shared operation and behavior |
|---|---|
| `POST /v1/sessions` | Open an application session; return its ID, binding and expiry. |
| `PATCH /v1/sessions/{id}` | Close that session through the allowed status transition; it does not erase its history. |
| `POST /v1/checkpoints` | Portable checkpoint intake: project, stable client session, optional `app_session_id`, source refs and manifest refs. Same contract in lite and gateway. |
| `POST /v1/manifests` | Idempotent bounded manifest chunks and closure under A3's wire contract; source evidence only, never caller-assigned origin. |
| `GET /v1/installations/{id}/controls?after={cursor}` | Bounded cleanup/control feed or reset snapshot, authorized only for this installation; no application session or memory content. |
| `POST /v1/installations/{id}/control-acks` | Idempotent cursor and per-command purge status acknowledgment; cannot create a grant, delete server content or claim server-verified device erasure. |
| `POST /v1/memories` | `remember`: create an attributed own-project report, never a self-certified published fact. |
| `GET /v1/memories/{id}` | `get`: return an authorized active memory with revision and evidence metadata. |
| `GET /v1/projects/{id}/cards?view=working` or `view=published` | Return only the view allowed to that caller; cross-project agents cannot request working memory. |
| `POST /v1/projects/{id}/card-patches` | `propose_card`: submit typed changes and field read/write dependencies; the shared pipeline determines application/publication. |
| `POST /v1/briefs` | `brief`: compute a bounded brief from explicit role/project/budget inputs; return `200`. This creates no memory claim or publication. |
| `POST /v1/corrections` and `POST /v1/undo-requests` | Owner-only attributed corrections or selective compensating changes. |
| `PUT /v1/projects/{id}/pins/{field}` and `DELETE` on that pin resource | Owner-only pin/unpin with expected versions. Removing a pin does not delete its memory. |
| `DELETE /v1/memories/{id}`; `POST /v1/redactions` for other supported target types | Owner deletion: commit logical denial and tracked purge work; do not report physical erasure as complete. |
| `GET /v1/audit/events`, `/v1/audit/traces/{id}`, `/v1/audit/diffs/{id}` | Authorized activity, trace and revision-diff inspection; bounded cursor pagination and purge-aware responses. |
| `POST /v1/audit/verifications` and `/v1/audit/sample-labels` | Owner-requested integrity verification or optional sample label; neither is a routine approval. |
| `PATCH /v1/projects/{id}/automation-policy` | Owner pause/resume through a revision-checked control resource. |
| `/v1/projects`, `/v1/connectors`, `/v1/policies` | Owner-only enrollment/configuration resources; the OpenAPI contract lists allowed create/read/update/de-enroll transitions. No usable credentials appear in responses. |
| `POST /v1/exports`, `/v1/imports`, `/v1/restore-jobs`; `GET /v1/jobs/{id}` | Owner-only export/import/isolated restore and authorized job status. Restore must obey Build §11 before serving data. |

**One logical operation across both interfaces.** Normalize each permitted REST/MCP request into the same versioned application command before checking idempotency. Include the operation, full meaningful payload and explicit scope in its hash; exclude transport request IDs and equivalent wire syntax. REST carries the application key in `Idempotency-Key`; MCP carries `idempotency_key`. Repeating a write through the other interface with the same stable client, logical session and key has one effect. Reusing that key for another command fails. For session creation, use the caller's `client_session_id` because the server handle does not yet exist. Retries recheck current authorization and redaction before returning a stored outcome.

**Concurrency.** Card patches carry expected field revisions and read dependencies in the body, exactly as Build §7 requires. Do not introduce mandatory whole-card `If-Match` checks that reject independent field changes. Use `ETag`/`If-Match` for an individually versioned control resource where whole-resource comparison is intended. Return `409` for application field/dependency conflicts and `412` for a failed HTTP precondition, with no disclosure of unauthorized current values [R14].

**Response contract.** Use `201` plus `Location` for a newly committed resource, `200` for an immediate result, and `202` plus an authorized job URI only after durable job acceptance. A mutation response distinguishes `accepted`, `applied` and `published`; HTTP success never implies all three. A deletion response reports committed denial separately from server purge, backup expiry, each installation's pending or client-attested purge, and external-copy limits. Stable error codes accompany `application/problem+json` responses [R15]; MCP maps the same domain codes into its result/error envelopes. Bound requests, pagination and rates; return `429` with retry guidance when throttled. No state-changing business operation uses `GET`; read audit events are allowed. Protected responses use private/no-store caching. Keep secrets and request bodies out of access logs, and never put credentials in URLs.

**Migration contract.** Lite and gateway share versioned intake/control paths, envelopes, errors and receipt semantics. Preserve owner/installation/client-session identities, idempotency receipts, manifest IDs, control sequence epochs and acknowledgment positions at cutover. Re-enroll the credential provider, including the separately scoped cleanup grant; do not change payload identities or retry keys. No hidden API-key fallback enters the gateway. Test both an accepted pre-cutover intake retry and a partially applied deletion feed resumed after migration: no duplicate effect, lost denial or cursor rollback.

**Release parity.** Run shared command fixtures through both adapters, including REST-write/MCP-read and MCP-write/REST-read. The same authorized snapshot, rendering inputs and caller context must produce the same memory result after envelope normalization. Audit records retain the interface, request and trace IDs while sharing logical operation identity. CI regenerates OpenAPI and MCP tool schemas from the shared domain definitions and rejects drift; examples and both adapters must validate against those generated schemas. First-class REST does not require a second service, datastore or authorization system.

### Build §4. Connector intake, deduplication, secret scrubbing and bootstrap

**Secret scrubbing is a release requirement.** Inspect all service-controlled content-bearing intake—reports, checkpoints, connector responses, imports and model responses—before durable payload storage, queues, audit bodies, temporary files or backups. The local capture integration also reduces/scrubs before its spool and before network dispatch; server-side scrubbing remains mandatory. The client's pre-existing transcript store is outside this service's scrubbing guarantee and is read locally for reconciliation, never uploaded wholesale. Strip configured credential fields and supported token/private-key patterns; replace matches with typed redaction markers, keeping only detector/version and non-content counts. Raw suspected secrets are not retained in quarantine. If the scanner fails or cannot safely parse an input, reject it or retain only a non-content failure envelope. Reverse proxies and exception handlers must never capture unsanitized bodies.

Run the scrubber again on the fully assembled request immediately before **every model call**, including extraction, judging, retries, repair and future engine/provider calls. This catches older stored content and secrets introduced by joins, query text or new detectors. Use the same dispatch path for all providers; a scanner failure blocks dispatch. Scrub model results on re-entry. Inspect exports and logging boundaries too. Usable service/source credentials stay exclusively in the secret store and are never substituted into model payloads.

Scrubbing does not prove that every possible secret is detectable. Version the supported patterns and encoded forms, record false positives/misses in seeded tests, and reject unprocessable attachments. If scrubbing removes evidence required by a predicate, mark that candidate unsupported rather than verify altered meaning. Use provider revisions or a keyed digest calculated transiently for original identity where necessary; persist only scrubbed evidence and span/redaction mappings. REL-04 checks intake storage, jobs, WAL/backups, model request capture, logs and exports with synthetic tokens, benign lookalikes, scanner outages and assembled-prompt cases. No real credentials enter these tests.

**Typed identifier exceptions.** Entropy alone must not scrub valid commit SHAs, CI run IDs, content digests or UUIDs. Allowlist these classes only in their declared schema paths and validated source context: registered-repository commit IDs with the provider's exact format; configured-provider run IDs; algorithm-tagged digests of admitted scrubbed content; and parsed UUIDs for service/source objects. Preserve their exact bytes and case where meaningful through intake, storage, verification and dispatch. An arbitrary high-entropy string in prose is not an ID because a caller labels it one. Explicit credential-field rules and known-secret matches take precedence; reject an ambiguous ID/secret collision instead of silently accepting or rewriting a value needed for verification. REL-04 includes valid examples of each class, an injected secret inside an ID-shaped field, malformed IDs, embedded credentials in prose and a mixed valid-ID/secret report. Verify that real identifiers survive unchanged and secret fixtures do not.

Every connector declares endpoint/account, protocol adapter, provider scopes, allowed tools/resources/arguments or HTTP methods/routes, object identity, project mapping, source trust ceilings, default policy, permitted processors, pagination/change-feed strategy, timeouts, retry limits, retention and schema/version. Returned tool descriptions and safety annotations cannot change these settings. Unknown tools, changed schemas and unconfigured routes remain disabled. Record coverage gaps, cursor position and last successful synchronization.

Missing per-object policy inherits the explicitly enrolled connector policy only where that policy covers all its admitted objects. Unknown provenance, out-of-scope objects or an unclassifiable exception still fail closed. A missing required policy mapping is a connector defect: bounded retry, seven-day payload expiry and one aggregated status alert per connector. Never turn it into a per-item owner task or use a permissive inferred default.

**Version identity:** use `(connector, account, object, source_revision)` where the revision is trustworthy. Otherwise compare a versioned canonical content hash with the object's last accepted hash. Exclude documented volatile retrieval metadata, preserve meaningful value/case differences, and store scrubbed evidence privately where permitted; usable secrets are never an evidence-retention exception. Unchanged polls update sync health and applicable verification timestamps but create no new claim revision or independent corroboration. Retrieval time is observation metadata, not version identity.

For unversioned sources, A→B→A is a new observed transition, not discarded because hash A appeared earlier. Allocate a local observation sequence when content changes from the preceding observation; serialize per-object fetch/application so late overlapping polls cannot roll state back. A job retry retains its observation identity. Polling cannot recover unseen intermediate versions; record that limitation. An exact match with a previously deleted identity is blocked by the deletion ledger. A 404 or permission failure is not proof that source content was deleted.

Agent events use `(owner, stable_client_id, client_session_id, idempotency_key)` and the complete semantic command hash. Same key/same command returns the prior authorized outcome; same key/different command fails. Credential rotation does not create another event. Independent reports with identical text remain separate but do not count as independent evidence. Build §3.1 defines canonical command normalization across REST and MCP; changing interfaces never creates a new event identity.

**Cold start:** enrollment creates an empty typed card and `not_yet_published` state. Fetch registered `CLAUDE.md`, `AGENTS.md` and README files, when available, at an identified revision; combine with the first authorized session's structured report. Populate bounded working descriptions as `reported` unless an explicit field verifier establishes stronger support. Native instruction files are source data inside this service, not instructions to its workers. File names, presence on a branch or a model's confidence do not prove trusted authorship. Missing files leave unknown fields rather than invented content. Publish verified fields only under Build §5–Build §6 and advisory lessons only under Build §6.1; an initially empty publication is valid and visible to its owner.

### Build §4.1 Narrative origin, file provenance and capture completeness

Apply this initial conservative contract to **all free-text working reports, focus/purpose/open-thread fields, summaries and advisory candidates**. Scrubbing does not establish origin. Tool authentication, repository ownership, commit signatures and last authorship cannot clean copied or summarized text. Ordinary dependency reads, pasted traces, missing ancestry and abrupt endings may leave almost no eligible prose. Measure that loss against all important handoff needs. Optional owner contributions cannot compensate for it: an empty automatic narrative lane fails the intended product outcome.

Keep three decisions separate: **permission** determines whether input may be processed/shared; **evidence status** records support, contradiction or uncertainty; **operational authority** controls permissions and consequential actions. Permitted information need not be trusted as instructions, and first-party origin does not establish truth. This release still excludes mixed/unknown narrative from automatic delivery. A2.3 tests a distinct lower-trust policy in isolation; until separately earned and implemented, broad learning from ordinary mixed-source coding sessions is deferred.

**Activation boundary.** `client_narrative_enabled` defaults to false in lite and the gateway. Enable it only for a pinned client/capture profile after the file-provenance, input-coverage, closure/reconciliation and local-delivery fixtures below pass on that integration. This applies to own-project automatic working text as well as advisory candidates; enabling the advisory lane alone cannot bypass it. Controlled server workers may supply separately proven closed input sets without depending on client capture. Direct owner notes use the owner channel below. S0 may collect incomplete client evidence and run isolated diagnostic reads while this production path stays disabled. S0b-2 may exercise simulated eligibility on independently checked frozen provenance/reconciliation records without a deployed uploader; account for preparation effort, and do not count that as passing production integration. A passing fixture is bounded evidence, not proof against a compromised client.

**Optional owner contributions and endorsement.** Preferences, decisions, notes and corrections may supplement automatic memory; their creation or maintenance is never required for the product acceptance case. Accept a first-party owner contribution only through a deliberate authenticated owner action that records project, exact immutable revision, author declaration, declared external inputs and time. Use an admin context unavailable to ordinary agent/hook credentials; an unattended same-user helper that an agent can invoke is not an owner-presence boundary. Require a fresh owner action bound to submitted bytes. Scrub before storage; changed content creates a new revision and cannot reuse its declaration. Known mixed/unknown dependencies cannot be cleared by a checkbox, pin, signature or import. Endorsed agent/third-party text retains its origin plus a separate endorsement label. Owner attestation is an assumption about the declaration, not independently proven authorship or semantic truth.

Do not enroll an agent-writable repo note as an automatically trusted owner channel. A byte-identical local copy may refer to an existing immutable owner note only when the observed revision and provenance binding match; subsequent edits require their own provenance. Signing all commits—even with a hardware key—does not show that their text was originally written by the owner. No “signed means first-party” rule is permitted. Missing owner-channel isolation keeps the note unknown; do not add a silent bearer-token shortcut.

**File-version provenance ledger.** For eligible repository reads, retain a private record keyed by owner/project, repository/worktree, canonical path and exact content revision/digest. Record predecessor revision, successful write event and writing root session, source/input dependencies, origin/assurance basis, provisional/final state and capture-profile version. Keep original-byte identity distinct from scrubbed payload identity; use a keyed digest where original sensitive bytes must not be retained. A hash identifies a version, never its trust. Copy, rename, commit, checkout or a familiar git author cannot reset known taint.

Track confirmed successful `Write`/`Edit` effects, not just attempted calls. A partial edit conservatively inherits the previous file's provenance plus the writing session's inputs. An arbitrary replacement also retains prior/session dependencies unless an instrumented deterministic operation establishes an exact replacement from an already admitted source. While the writer is active or unreconciled, its outputs remain provisional/unknown. Later taint or evidence invalidation propagates to file revisions, later reading sessions and derived memories. Store dependency edges so the change cannot strand a falsely clean downstream revision.

`Write`/`Edit` are not the whole write surface. Shell commands, formatters, generators, checkout/merge operations, parallel agents and outside processes can change files. Bind each read to the actual bytes/revision it consumed, using an observed result or isolated immutable snapshot; a pre-read filename/hash followed by an unobserved change is insufficient. Unattributed mutations, ambiguous concurrent writers, unresolved symlinks or missing/mismatched ledger entries make that read unknown. A watcher can reveal changes but does not by itself identify their author or capture every intermediate version. Unsupported shell/file paths remain unknown rather than requiring a general shell dataflow engine for S0.

Historical transcripts may reconstruct observed writes and known taint where exact effects, versions and ancestry exist. They cannot prove absence of unrecorded writes or recreate missing historical bytes. A legacy file with no reliable history is unknown unless it is explicitly supplied through the owner channel with its honest origin declaration; there is no automatic clean bootstrap. Ledger retention/purge is dependency-aware: if required provenance is no longer available, dependent automatic narrative becomes ineligible rather than being treated as clean.

**Versioned read classes.** Configure the resource class and exact input/operation binding, not a permissive path or tool-name prefix.

| Read class | Admission rule |
|---|---|
| Repository file with provenance | Match the exact observed file revision to the ledger. Inherit that revision's origin and dependencies. Only a resolved eligible first-party chain can avoid taint; an owner repo, signed commit or absent ledger entry cannot supply that chain. |
| Explicit owner note | Read the immutable owner-channel record with `owner_asserted` / `owner_attested` labels and its declared origins. It is data, not policy or verified meaning. No automatic trust for an editable repo copy. |
| Registered local test result | Identified runner/code/test/fixture revisions and classified inputs. Structured counts/status may retain exact typed authority; narrative output needs source provenance. Arbitrary stdout, dependency traces, fixture echoes and network results are not inherently clean. |
| Allowlisted structured source observation | Exact Build §5 fields retain their narrow authority. Free-text titles, errors, comments and tool descriptions are classified separately. |

**Local capture and non-tool inputs.** Use a local command hook that parses input, reduces it to bounded metadata and scrubs before writing the local spool (A3). Never send raw hook JSON directly to the cloud: HTTP hooks send their input as the POST body [R20]. Do not log full input on parser failure. Original client transcripts may already contain sensitive material; this service neither uploads them wholesale nor claims to scrub the client's own historical storage. Reconciliation reads them locally and retains only permitted reduced evidence.

The manifest identifies root/session/parent, installation, client and hook/schema versions, tool IDs and outcomes, file revisions, input-origin classes, event ordering, checkpoint coverage and terminal/reconciliation evidence. A counter generated by the hook alone cannot establish completeness. Include these non-tool paths in the supported-client matrix:

- Classify loaded instruction files by resolved path, revision and ledger/source origin, including nested/vendored rules. `InstructionsLoaded` is observational; the current docs also exclude direct Project-instructions `AGENTS.md` loads from that event. Inventory such startup/configured inputs separately or mark coverage unknown [R20].
- `UserPromptSubmit` may carry scheduled work, subagent reports or inter-session messages. Classify the actual source and inherited dependencies, not the event name. Paste markers are hints; their absence does not prove owner authorship [R20].
- Use `SessionStart.source` to detect startup/resume/clear/compact/fork, then resolve actual parent/root IDs and inherited input revisions from supported client evidence. The source enum alone is not a complete ancestry graph. Missing ancestry, subagent transcripts, expanded skills or other unenumerated context remains unknown [R20].

**Capture profile to freeze on day 1.** Use local `type: command` handlers with `async` and `asyncRewake` omitted, `timeout: 1` second, and `onFailure: continue` where supported. Set the collector's internal/process deadline to **750 ms**, measured from OS process start and including interpreter/runtime cold start and imports, leaving nominal headroom before the one-second host timeout. Do not start the budget only when handler logic begins. It only reduces/scrubs metadata and commits a local spool record; no network or model work. Stop new work when the internal deadline expires and attempt bounded cleanup without claiming capture. A successful receipt is written only after the record reaches its promised durability boundary.

The 250 ms margin is a design allowance, not a guarantee that scheduling or storage completes in time. Use a crash-safe append/transaction format; test interruption before, during and after commit/fsync, receipt loss and restart reconciliation. Never classify a partial write as accepted or a missing receipt as clean coverage. Keep reconciliation/upload in supervised workers. Record process-start-to-durable-receipt p95/p99 latency, cold-start time, failures, internal cancellations and host kills; report timed-out/failed attempts separately rather than dropping them from latency accounting. If p99 leaves insufficient headroom, prefer a small compiled collector and remeasure within the same cap; do not relax the deadline or claim untested coverage. Unsupported settings or handlers disable the affected profile; do not silently change mode or increase deadlines.

Record this capture measurement block per installation; the execution sheet carries the same fields. Mark unmeasured values unknown. Cold-start and end-to-end measurements include process/interpreter startup; preserve sample count and cold/warm mix.

| Capture measurement | Run record |
|---|---|
| Cold-start time | ___ ms; sample count and cold/warm mix: ___ |
| Process-start-to-durable-receipt latency | p95: ___ ms; p99: ___ ms; failures/timeouts: ___ |
| Effective SessionEnd timeout | Overall: ___ ms; collector host timeout: ___ ms; effective configuration source: ___ |
| Competing SessionEnd hooks | Hook identities and configured timeouts: ___; joint-run result: ___ |

`onFailure` cannot gate async hooks; ordinary `async: true` hooks also lack the configured timeout enforcement. Observational events may be dispatched independently regardless of handler settings [R20]. Therefore eligibility depends on durable receipts plus closure reconciliation, never on presumed synchronous event order. Capture failure need not stop coding; it must prevent a clean memory-eligibility claim. A hook that never ran cannot report its own absence. Do not emit agent context, approval, retry-permission or control decisions from this metadata-only collector.

Use this minimum capture matrix and pin the installed schema [R20]:

| Event set | Required capture interpretation |
|---|---|
| `SessionStart`, `SessionEnd`, `Stop`, `StopFailure` | Preserve ancestry and distinguish terminal evidence from turn completion/failure. |
| `UserPromptSubmit`, `UserPromptExpansion`, `InstructionsLoaded` | Bind actual input origin; retain the separate startup/instruction inventory. |
| `PreToolUse`, `PermissionRequest`, `PostToolUse`, `PostToolUseFailure`, `PermissionDenied` | Correlate attempts, decisions and outcomes by tool ID; failure may have partial effects. `PermissionDenied` covers auto-mode only. |
| `PostToolBatch` | Reconcile batch membership against individual calls; reduce its potentially content-bearing payload locally. |
| `SubagentStart`, `SubagentStop` | Bind `agent_id` to parent and child evidence; track unmatched lifecycle records. |
| `PreCompact`, `PostCompact` | Preserve ancestry/dependencies across compaction; never reset taint. |
| Optional prototype: `CwdChanged`, `DirectoryAdded` | Record directory/scope changes and re-inventory possible instruction inputs; do not treat these events as comprehensive coverage. |

Manual denials, configured deny rules, cancellations and hook-blocked calls need their actual result/transcript evidence; absence of `PermissionDenied` proves nothing. Treat unexplained attempts/outcomes as unknown, not unexecuted. Keep failed writes provisionally tainted until their effects are established. Batch completion is neither session closure nor proof of atomic tool execution. Deduplicate by event/session/agent/tool identity, not callback arrival order. Missing events in the installed version, unavailable child logs or uncovered input paths remain explicit gaps. Day one implements only the bounded metadata subset it can verify; full-profile completeness is a later gate.

**Directory coverage limits.** `CwdChanged` and `DirectoryAdded` are observational signals [R20]. Keep startup and final permitted-root inventories as well: a missing event is not proof that no root/instruction context changed. If optional prototype coverage is unfinished, those paths remain unknown; optional instrumentation is not an exemption from production input coverage. Classify newly encountered instructions by their source/revision and retain inherited taint.

**Installation coverage.** Cloud sessions do not inherit the laptop's `~/.claude/settings.json` [R20]. Select a project-scoped configuration or enabled plugin that actually reaches the target runner, or mark that installation unknown. For each local, cloud or second-device installation, record client/build, configuration source/digest, script/plugin revision, allowed execution mode, transcript access and observed test receipts. Run a small successful/failed/denied/interrupted/subagent/compaction smoke matrix on each claimed profile; unsupported cases stay unknown. A shared project file or enabled-plugin label is not evidence that capture ran. Credentials remain installation-scoped and outside committed hook configuration. A second device may prove authorized reading without proving capture there; report those separately.

**Closure reconciliation.** A successful SessionEnd callback is a termination observation, not a clean-origin certificate. A separate local reconciler runs after closure and allows for transcript lag. For the pinned format, compare hook and transcript tool inventories keyed by session/subagent plus `tool_use_id`, including outcome and relevant resource bindings; a set of matching IDs alone is insufficient. Reconcile child/parent linkage and required non-tool input inventories separately. Unmatched events, missing outcomes, unexplained duplicates, contradictory file versions or missing input classes mean incomplete coverage. Known denied/unexecuted attempts must be distinguished from executed reads/writes. A transcript-only event may repair a gap only if the format actually supplies all required evidence; otherwise keep unknown.

Retry reconciliation for a bounded five-minute initial window after observed termination, without blocking the interactive client. Require the pinned profile's tested terminal/flush evidence and complete required inventories; repeated stable EOF or a fixed sleep is not proof of completion. If the client format cannot establish these, disable eligibility for that profile. A missing terminal event after a crash/disabled hook, transcript truncation, an unavailable child log or unresolved lag leaves the session unknown. Late contradictory evidence invalidates previous eligibility and descendants. Submit it as a new immutable coverage revision tied to the same root; never replace the old record or reset ancestry.

**Failure behavior and trust limit.** Current hook documentation supports `onFailure: "block"` on eligible command/HTTP hooks from v2.1.295, but observational/asynchronous events cannot all gate execution [R20]. Pin/test actual behavior. For memory-only capture, allow ordinary coding to continue where appropriate and fail closed on **memory eligibility**, not by silently declaring a complete manifest. Reconciliation detects observable capture failures; it cannot detect facts absent from both channels or protect against a same-user attacker modifying both. Complete client evidence is still `client_attested`, requiring an honest client and trustworthy transcript under the declared threat model. No remote attestation or Q10 enforcement guarantee is inherited. A controlled worker may provide `server_observed` evidence; owner submissions remain `owner_attested`.

**Taint and delivery.** Third-party-writable narrative exposure makes the session mixed; incomplete/unclassified input makes it unknown. Preserve both reasons when applicable. Fork/resume/compaction, file writes and derived summaries inherit the union of dependencies. Active/unreconciled client output is provisional. Automatically deliver only first-party narrative with current provenance, complete reconciled coverage and an enabled supported profile. Each unit displays origin, assurance, revision/root session and coverage time. Mixed/unknown data gets a non-content marker plus an authorized explicit same-project inspection reference; an explicit read quotes it as untrusted data and taints derivatives. Owner inspection/export remains purge-aware. No new prose-sharing exception is introduced: Build §6.1 still governs advisory publication and Build §10 governs automatic checks and scoped pauses; owner-review recency is not an availability condition.

**Release evidence.** Required counterexamples include poisoned text written to a repo then read by another session; partial edit/copy/rename/revert; shell/external/concurrent changes; missing/late write records; owner signature or endorsement of copied text; omitted hooks with consecutive local counters; disabled hooks; transcript lag/truncation; missing child/non-tool inputs; and interrupted capture/upload. The ledger/reconciler/uploader require implementation and runtime evidence. Without passing evidence, keep client narrative disabled. Typed observations and optional owner context can support diagnostics, but do not establish automatic knowledge reuse. Report withheld useful context, empty briefs and capture gaps without manufacturing eligible sessions.

**Availability boundary.** Initial client-derived narrative supports reuse only after session closure and successful reconciliation. Accepted checkpoints during an active session remain provisional; acceptance is not availability. Verified source observations can update independently. A future bounded-checkpoint capability needs independently attributable input/effect boundaries and its own release evidence; cutting a session ID or declaring a clean prefix cannot bypass later taint propagation. Measure discovery-to-first-authorized-availability, including active-session duration, reconciliation, offline delay, upload and generation. Record the earliest evidenced discovery time and its uncertainty; unavailable discoveries remain in the denominator. If this delay defeats the parallel-agent use case, the first-release scope fails that requirement rather than claiming immediate sharing.

### Build §5. Subject authority and preventive verification

Each subject definition includes type/cardinality, allowed source operations, authority order, exact predicate, freshness, permissible transitions, maximum audience and required dependencies. There is **no universal repo > ticket > report ladder**. Scope determines authority.

| Subject/example | Authoritative observation | What it does not establish |
|---|---|---|
| `repository.head` | Registered repository API resolving a named protected branch to a commit. | That the commit is deployed, correct or approved as a policy. |
| `ci.result` | Configured CI workflow result for that exact repository/commit/run. | All tests passed, the feature works, or another commit is safe. |
| `issue.state` | Configured issue API's enum for that issue and observed revision. | The underlying problem is solved or a comment is a project decision. |
| `release.version` | Configured release/deployment system for the named environment. | Repository tags alone do not prove production deployment. |
| `convention.<key>` | Structured key in an explicitly designated authority source, using a fixed vocabulary/verifier. | Arbitrary README prose, PR text or inferred preferences are not policy. |
| `decision.<key>` | Structured decision registry with an identified decision ID/state and permitted enum value. | Agreement between agents or issue comments is not organizational adoption. |
| Working `focus`, `purpose`, `open_threads` | Direct agent/owner reports with their own provenance. | These are not automatically publishable facts. |

Implement only subject/source pairs available through the first connector and useful in the probe. Unsupported subjects remain working reports or absent. A commit-existence check cannot validate the broader sentence “feature shipped.” Validation must check the **whole predicate**, including object, environment, value, time and source scope.

For inherently owner-defined subjects, a standing rule may designate an authenticated typed owner command as the authoritative source—for example, the owner's declared convention enum. The verifier establishes who declared which value, not an external fact such as a deployment. That optional direct correction can publish under the existing audience rule; it does not turn agent candidates into an owner approval queue. An owner assertion about an external system still needs that subject's external evidence.

Connector trust is a ceiling, refined per operation and field:

- **Untrusted narrative:** third-party-writable issue bodies, comments, PR descriptions, documents and email may produce only attributed claims about that source. They cannot create decisions, conventions, preferences, grants or instructions. An authenticated API does not upgrade the prose it returns.
- **Structured source observation:** allowlisted typed API fields can support the exact machine-readable predicate defined for that subject. A third party changing an issue's state can establish what the issue currently says, not a new general truth.
- **Designated authority:** an owner-enrolled structured registry/configuration source may define its explicitly assigned subjects. Its revision, write protections and relevant provenance are checked; choosing this source is a configuration decision, not recurring review.
- **Agent/model output:** maximum `reported` until an independent source verifier checks the precise claim. Advisory eligibility is separate under Build §6.1 and never upgrades that evidence level. Multiple models, prompts or agents citing the same origin are not independent corroboration.

Source class is not a scalar that upgrades every field. Model extraction and model judging can reject or flag a candidate; they cannot bypass a missing deterministic source predicate for verified publication. Build §6.1 defines the only experimental route for publishing explicitly unverified advisory meaning. Genuine independent sources may be combined by a preconfigured subject verifier, but “two models agree” is not an S1a publication route. Disagreement between coequal authoritative sources yields one bounded contested marker, with evidence accessible to authorized readers. A weaker report is a challenge, not equal competing truth. A valid newer transition from the same authoritative object replaces its older observation according to that subject's rule.

### Build §6. Verified typed publication and injection boundary

Cross-project **verified-lane** publication requires all of: permitted subject/type; current source support under Build §5; exact candidate validation; valid source/rule/policy/pin dependencies; freshness; no unresolved authoritative conflict; existing disclosure rule; rate/change budget; and final transactional checks. `reported` claims remain in the originating project's working context unless they satisfy the separate experimental advisory contract in Build §6.1. Owner corrections also obey the publication predicate; a direct edit never becomes an evidence bypass merely because it is pinned.

The verified tier of published cards is a bounded bundle of typed fields, not free-form agent prose. Advisory text, if earned, is a distinct tier and never inserted into these fields. Initial grammar: enums, booleans, bounded numbers/timestamps, validated object/commit IDs and canonical source references. Decisions/conventions use configured keys and enum values; arbitrary instructions or summaries do not fit the grammar. Limits: at most 12 fields, at most 5 items per additive field and at most 160 characters per validated identifier/reference component. The renderer emits fixed templates as quoted JSON/data and generated labels. It does not copy source titles, Markdown, arbitrary URLs, code, shell commands, imperative text or tool directions into published values. Canonical links are generated from enrolled hosts and validated IDs; they do not trigger automatic fetching.

These constraints are structural, not a promise that a natural-language “imperative detector” catches injection. Unknown values stay in working reports or are withheld. Inputs cannot nominate tools, change prompts/configuration, enroll connectors, remove pins or disable audit. Extractor/judge workers receive only bounded data and the capabilities necessary for their job, not owner credentials or external write tools. Adversarial tests cover instruction text in source bodies, tool metadata, identifiers, URLs and apparent schema fields. Consumers still need an instruction/data boundary; the service cannot guarantee how an external agent interprets even valid data.

A standing owner disclosure rule names admitted source/project classes, allowed fields, fixed audience and processor constraints. Evaluate every source and the exact output against it. Raw read access does not imply derivative sharing. An unlisted source, rule expiry or tightened policy blocks the affected field. Models cannot widen grants. Exact-output owner exceptions are optional administrative changes, not an automatic queue fallback.

Maintain separate **working head** and **published bundle**. A bundle pins exact field revisions; it need not equal the current working card. Failed candidate fields leave the last still-eligible published version in place. Stale published fields display age until their configured expiry, then become unavailable. Revocation, redaction, evidence invalidation or withdrawal removes the affected field immediately; never fall back to an older version. Unaffected fields can remain available. Each new bundle records the final field set and its dependencies.

Publication status carries a current eligibility/verification reference separately from immutable claim content. A successful unchanged authoritative recheck may renew the applicable check/expiry with an audited event, without pretending the fact changed or creating another evidence source. A contradictory owner pin invalidates an older incompatible publication even if the pinned replacement has not qualified for publication.

Initial freshness defaults: volatile CI/issue/head observations must be rechecked within 15 minutes before publication and carry a 24-hour display expiry; enduring convention/decision facts get a seven-day recheck and 30-day display expiry. A registered immutable historical observation can remain valid as “CI passed for commit X at time T”; it must not be relabelled “current head is green” without a current-head dependency. Set subject-specific values during the probe. A rewrite or unchanged poll does not manufacture a new event; a fresh authoritative check records `last_checked_at` separately from `last_changed_at` and `last_supported_at`.

### Build §6.1 Experimental advisory lessons: anchors checked, meaning unverified

**Status and scope.** Disabled until S0b-2 passes and the owner enables this lane for the enrolled personal-project group. This is a standing configuration choice; eligible lessons then publish automatically without item approvals. It is not available to employer/client or mixed-policy projects. S1a-lite must use the same lane gate if it serves lessons.

| Field | Bounded contract |
|---|---|
| `category` | One enum: `failure`, `rationale`, `workflow`, `gotcha`. |
| `text` | Plain text, 1–240 Unicode code points. Describes a lesson or hypothesis; it is not an instruction with execution authority. |
| `applicability` | One or two explicit conditions, each ≤120 code points. Missing conditions block sharing; their truth in the receiving task is not verified. |
| `invalidation_conditions` | One or two conditions, each ≤120 code points, plus `expires_at` no later than 30 days after authorship. |
| `evidence_refs` | One to three canonical project-scoped references to retained, revision-addressed observations. At least one observation must be a distinct retained record; self-citation alone fails. This is not independent corroboration. |
| Protected metadata | Gateway-assigned lesson ID/revision, originating project, author, input-origin bindings, check timestamps, policy/audience and `semantic_status=unverified`. |

The checker proves only schema bounds, that **every anchor exists at the cited revision and belongs to the originating project**, and that origin, scope and lifecycle rules pass. It does not prove relevance, causality, semantic support, applicability or the lesson's conclusion. `anchors_checked` is never displayed as “verified lesson.” A model judge is a diagnostic, not this checker. Text in these fields conveys no tool-use authority, cannot authorize external actions or grant/pin changes, and never becomes a system instruction. This is an enforcement boundary, not a claim that a text classifier recognizes every imperative.

**First-party authorship means origin, not the last writer.** Apply Build §4.1. Eligible automatically generated lessons can come from a controlled worker or a closed ordinary session with reconciled input coverage and exact file provenance under an enabled capture profile, if the standing policy accepts its clearly labelled `client_attested` assurance. Direct owner lessons must use Build §4.1's exact-revision owner channel and retain any external-input provenance; they do not count as automated extraction success. Narrative derived from third-party-writable sources or unknown inputs is ineligible even after paraphrase or trusted-tool echo. Repository ownership, a commit ID or an enrolled agent alone does not establish first-party content. A1 screens existing transcripts on day 1, routes M/H ≥50% directly to the A2.3 decision, and otherwise permits one eligibility recheck before S0b-2. If those records cannot meet the frozen eligibility threshold, skip the first-party advisory model half; A2.3 is a separate explicit experiment, not an eligibility exception.

**Anchors provide traceability, not independent support.** An agent can create a commit, document or run artifact and then cite it. A distinct record may satisfy the anchor-existence rule while being self-authored, irrelevant or semantically misleading. Record author/creator relation, source revision and observed time; never count such an anchor as independent corroboration. A manufactured-but-existing anchor must pass only the narrow existence test and must fail any attempted promotion to verified meaning. Semantic fixtures and optional owner adjudication assess relevance and false rationale separately.

Render a separate **“Advisory lessons — anchors checked; meaning unverified”** tier after verified facts, using escaped quoted JSON/data. Include origin and assurance basis, age, applicability, invalidation conditions and canonical references. Plain strings may still influence a consumer: escaping, labels and short length do not eliminate prompt injection or mistaken generalization. Initial delivery limit: two complete lessons and at most 600 tokens inside the overall brief cap. Never silently upgrade them to decisions, conventions or verified facts; consumers receive no added capability. Evidence access remains permission checked and links do not trigger automatic fetches.

Recheck anchor availability and origin/policy eligibility within 24 hours before delivery; Build §10 adds automatic control-canary health and scoped pauses. Check current denial, permissions, expiry and known invalidation at every publication/delivery, including caches and direct routes. Owner absence alone does not pause either lane. A changed/deleted/denied anchor, expiry, correction or known invalidation withdraws the lesson and known derivatives immediately without fallback. Natural-language invalidation conditions are displayed, not claimed mechanically evaluated; unknown applicability remains advisory. Reuse/rephrasing does not reset authorship or expiry. Renewal requires new eligible evidence and a new revision. Effective expiry is the minimum of declared expiry, the 30-day authorship cap and earliest scheduled purge/expiry of any required anchor payload. A 25-day-old anchor with 30-day retention leaves at most five days. Rechecks do not reset clocks; longer anchor retention needs an explicit permitted policy. CAS, pins, rate limits, audit, scrubbing and deletion apply to both lanes. A pinned lesson can still expire or be withdrawn.

Treat each lesson as one versioned logical item for patch limits and CAS; text, conditions and anchors update atomically. Keep at most five active advisory lessons per project. Verified fields and lessons share the bundle/rate budget while quality accounting stays separate. Responses retain separate `verified_fields` and `advisory_lessons`; legacy consumers receive only verified fields unless they support advisory schema/labels. Owner corrections and controlled extractors use the same core; ordinary agent submissions cannot assign first-party origin or publish themselves.

**Automatic capacity policy.** Keep at most 20 pending advisory candidates per project within Build §10's overall pending cap, for at most seven days and never beyond their own effective expiry. Merge exact duplicates by retained identity/evidence without extending life. Explicit same-item updates use revision/CAS and pin rules; a new paraphrase does not create a new item or clock. Remove expired, denied or invalidated active items first, then fill empty slots from eligible pending candidates in acceptance order, with stable ID tie-breaks. If full, at most once per project per day admit the oldest eligible pending candidate by retiring the oldest activated unpinned active item; record both IDs, reason and policy version atomically with publication. This deterministic turnover is a testable baseline, not a claim to rank semantic usefulness. Rate limits and source/client admission limits still apply.

Never replace a pinned item automatically. If all slots are pinned, or the daily turnover budget is exhausted, retain bounded pending candidates until capacity opens or they expire. Reject excess before durable candidate acceptance with an explicit capacity result; accepted checkpoints remain accounted for even if no lesson is published. Retirement withdraws automatic delivery without erasing retained provenance/audit; deletion and expiry rules still dominate pins. Expose rejection/expiry/turnover, all-pinned saturation, repeated paraphrase attempts and useful targets lost to the cap. Require no owner slot curation for the unpinned baseline; owner-imposed saturation is visible degraded capacity. If the policy loses essential value or permits churn attacks, keep the lane disabled or revise and retest the bounded policy.

**Residual risk decision.** S0b-2 measures useful transfer, false rationale, inapplicable reuse, origin failures, poisoning and selective repair separately from typed correctness. First-party restrictions reduce attack surface but do not establish trustworthy meaning. Quoting and labels cannot prevent a consumer with existing tool permissions from acting on poisoned text; the service's read-only source connector does not constrain external agents. Test consumers with their representative capabilities mocked and claim only the boundary actually enforced. Publication, useful reuse and correction results stay stratified. If provenance cannot be enforced or useful unattended reuse fails, keep the lane disabled and rescope before a gateway build.

### Build §7. Field concurrency and transaction protocol

Every patch declares its **write set** and **read dependencies**: expected revisions for changed fields and every field/source/rule it relied on. Use gateway-recorded input snapshots for generated patches; do not trust a model to omit an inconvenient dependency. A proposal based on the whole card conservatively depends on the whole card. Owner pin versions, schema/policy epochs and source versions are always dependencies where relevant.

Different fields may commit concurrently when their declared and gateway-derived dependencies still match. Overlapping scalar updates conflict; the loser refetches/regenerates within bounded retries. Additive lists use stable item IDs and set-like additions: duplicate identity is idempotent, independent additions can commute, and edit/remove operations check the target item version. Revalidate list bounds and cross-field invariants against the **merged current state**. Do not silently trim a list to make a merge fit. One patch commits all of its effects or none.

This is application-level field comparison inside SQLite's serialized transaction, not multiple SQLite writers and not automatic semantic merge. A lease can reduce duplicate work but is not correctness. Whole-card revision remains an audit/order identifier; a stale whole-card number alone does not reject an otherwise independent field update.

**Write protocol:**

1. Authenticate and resolve the operation; persist intake/call intent as required. Fetch source data, run extraction and any model checks **outside** the write transaction. Persist source observations and immutable validation results with exact input/output hashes, source revisions and verifier versions.
2. Begin a short write transaction. Resolve idempotency against canonical rows. Recheck current identity/grants, tombstones, pins, source/rule/policy versions, validation expiry, field read/write sets and merged-state invariants. Only bounded deterministic checks run here. Never perform connector calls, model calls, external signing, remote backup or network waits inside it.
3. Allocate a logical `commit_seq`; write field revisions, working pointer, dependencies, audit event, durable retry outcome and outbox jobs atomically. Immediate publication may share this transaction **only** if all needed evidence/model work is already complete and current deterministic checks pass. Otherwise enqueue publication through the committed outbox.
4. Commit, then acknowledge IDs/sequence. A lost acknowledgement is resolved through the stored logical outcome, not another mutation. No success is returned before commit. Projection/export failure does not undo a committed write.
5. Deferred publication assembles a bundle from the latest eligible fields in a short transaction, validating exact field/rule/source versions. On pointer contention it recomputes the bundle; it does not regenerate unrelated model results. Recheck eligibility again at a delayed release boundary.

Configure a pinned SQLite build, foreign keys and tested WAL durability settings (`synchronous=FULL` initially). `commit_seq` is an application sequence, not a WAL frame or a replication batch ID. Synchronous canonical views update in the same transaction. Reads pin a committed snapshot; read-your-writes requires `snapshot_seq >= acknowledged_seq` or an explicit timeout [R6–R7].

### Build §8. Briefs, delivery and performance

Brief rendering is a pure function of authorized snapshot/sequence, renderer/config version, policy fingerprint, exact request time, role/project, digest cursor and budgets. A time bucket may affect ordering/age display, never decide whether a newly recorded field exists. Use stable role/field ordering and stable tie-breaks; no portfolio score or global corpus ranking is required.

Coder/reviewer briefs prefer the own-project working card with evidence labels, then selected authorized verified publications, followed by the separately labelled advisory tier only when enabled. Planner briefs prefer permitted published cards. Native project instruction files remain part of the client baseline; the memory service does not replace them. Working free text obeys Build §4.1 origin/taint, file-version provenance and capture-profile eligibility before selection, and carries origin plus assurance labels. Failed or missing reconciliation excludes client-derived prose even when every received chunk is well formed. Expect verified typed facts and explicit owner-channel notes to dominate; generated narrative may be absent. A nearly empty brief is a measured continuity gap, not proof that the product works. Escape and length-limit retained units; never insert them as system instructions. Mixed/unknown reports are absent from automatic briefs and extraction, though an authorized explicit local read can inspect them as untrusted data. Measure local poisoning, answer bias and useful context lost to this restriction separately from cross-project publication.

Default final caps are 2,000 tokens and 9,000 characters, reduced for the tested client when needed. Count wrappers, labels, references and fences. Include complete units only; an unresolved group is one marker rather than a selected winner. Same retained inputs produce identical bytes. Purge or current denial can make replay unavailable; no offline brief replay is supplied.

Before content delivery or model/connector dispatch, durably record intent/trace and order the final live denial check with the release start. Deletion committed before that boundary prevents release. Already handed-off content cannot be recalled, and “sent” is not proof of receipt. No network operation is held inside a database transaction; the dispatcher uses a short control gate/epoch check around release start, with crash recovery for uncertain outcomes. All sensitive destinations are preconfigured.

Initial performance SLOs, measured under the declared spike load, are: gateway render p95 ≤300 ms; accepted eligible capture → working update p95 ≤60 seconds; working field eligible for publication → publication p95 ≤60 seconds, excluding any configured grace delay. Track end-to-end source-change → delivery separately, including polling/provider time. These are targets, not measured results.

Do not hide stalled work by measuring only completions. Track pending-job age distribution/p95, oldest age, arrival/completion rates, backlog size, errors and blocked-state counts per scope. Separate intentional hold time, verifier latency, writer wait and transaction duration. A sustained rise in queue age is a bottleneck signal. Saturation applies per-project backpressure; owner corrections, deletion and control operations have reserved capacity. Bound reads/export jobs so they cannot starve writes or grow WAL indefinitely.

### Build §9. Audit, anchoring and owner controls

Every service-controlled intake, call, validation, application, publication, read, retry, no-op, failure, correction, deletion, configuration and recovery process has a correlated trace. Record actor/project/session/job/run/attempt, input source/revision references, connector/model/prompt/verifier versions, checks/reasons, before/after revision references, audience/delivery IDs, timestamps, outcome and available usage. Unknown information is explicitly unknown. This does not expose provider-private execution, hidden model reasoning, source history unavailable to the connector or external agent actions outside this service.

Canonical mutations and append-only audit envelopes commit in the **same transaction**. Normal code paths cannot edit old envelopes. Put sensitive bodies, arguments, diffs, explanations and URLs in protected purgeable payload storage referenced by opaque IDs. Do not log credentials or authorization headers. Audit writes are part of the short local commit; audit viewing is never on the critical path.

Record durable intent before external calls and delivery, then an outcome. Timeout/crash can leave `unknown`; reconciliation/retry is explicit. Do not claim exactly-once external effects. Source operations are read-only, and incoming memory writes are protected by application idempotency. Automatic jobs cannot dispatch without required local audit persistence.

**Anchoring:** produce a signed sequence/digest periodically, initially every hour, to separately permissioned storage using a separate signing-key reference. Show the last independently anchored sequence and unanchored window. An anchor upload hiccup degrades this status without stopping normal memory. After **24 hours** without a valid checkpoint, pause new automatic publication for affected storage scope; continue locally audited capture/working updates and owner controls within capacity. Resume automatically when a contiguous checkpoint is verified. A verified mismatch/truncation is an integrity incident, not normal lag: freeze affected automation and require owner acknowledgement after repair. Colocated hashes alone do not prevent an administrator rewriting history; signing/retention reduce specific risks, not all host compromise.

Use versioned digest segments and signed retention manifests so intentional envelope expiry and payload purge remain distinguishable from unexplained removal. Retained checkpoints cover event order and permitted retention transitions, not permanent availability of every old body. An idle service still emits the configured health/checkpoint status; it does not invent memory changes to advance a watermark.

**Owner surface:** an authenticated activity list, expandable source → call → check → change → publication/delivery trace, revision diff and operational status. Filters by project, connector, agent, action, time and outcome; API equivalents remain usable if the console fails. Display expired/purged payloads as unavailable. Inspection does not claim deterministic replay of model output.

Owner corrections create attributed revisions and default pins. Automation never removes a pin. If newer authoritative evidence contradicts it, add `stale_pin` with source/time and surface it in the optional digest. A challenged pinned verified field loses publication eligibility unless its subject's verifier still supports the pinned value; the local pin remains. Advisory lessons with a confirmed contradiction or invalidation withdraw under Build §6.1; pinning or rechecking anchors cannot clear a semantic incident. Deletion/permission withdrawal can remove pinned content. Pinning is an owner preference about replacement, not authority over external reality.

Undo is a selective compensating patch with dependency checks. Preserve unrelated later changes; conflict with a later same-field change yields a safe no-op/report instead of overwriting it. Invalidate/recompute known derivatives. Undo cannot resurrect tombstones, widen grants or reverse actions an external agent already took. Owner-requested pauses persist until the owner resumes; automated cooldown must not override them.

### Build §10. Bounded operation, sampling and advisory availability

**State machine:** queued → processing → applied/published, no-change, failed, blocked or expired. Transient work retries at most five times with bounded backoff within one hour. Ambiguous attribution uses Build §2's three attempts. Policy-blocked or unsupported candidates wait for an actual source/configuration change until their seven-day expiry, not repeated model retries. At most 1,000 pending candidates per project; reject excess with backpressure, preserving a compact audit reason. Never silently drop acknowledged durable memory. Send no per-item approval prompts; aggregate status in the console/digest.

**Initial publication limits:** at most 3 changed fields per patch and 10 automatic bundles per project per hour. Independent rate limits apply globally to the configured sharing group. Hold/coalesce superseded eligible versions while preserving audit; never bypass limits by splitting one logical batch. Revocation, redaction and security withdrawal bypass publication throttles. A fivefold change-volume increase over an established baseline, repeated failed verifiers, or an attempted out-of-schema/authority effect triggers the affected-class breaker. Until a baseline exists, absolute limits govern. Tune only through versioned configuration, not model judgment.

An optional **15-minute grace window** can delay otherwise eligible cross-project publication during rollout, automatically ending after 14 days. Default is zero. A veto is an owner intervention, never a required approval; no response releases the still-eligible output. Recheck current source/policy/pin/rate limits at release. Grace is not a correctness mechanism when nobody watches, and its delay is included in the user-visible freshness metric. Immediate denial/withdrawal is never delayed.

**Automatic quality evaluation:** executable/source-keyed checks come first. When model judging helps diagnose semantic output, use a different model family from the generator where available and record that choice. Separate families still have correlated errors; judge agreement does not establish source truth. Verified publication remains bound to the deterministic subject predicate; advisory publication uses Build §6.1 origin/anchor checks without a semantic-truth claim. Known-wrong/injection fixtures run in isolation and cannot modify live memory.

Rechecking with the same verifier can detect new source state but does not independently establish that the verifier is correct. Quality evaluation also uses frozen expected predicates and independent fixture/oracle code; never grade a publication gate solely by asking that gate whether its own output passed.

**Optional, lane-stratified sampling.** Each week draw up to 20 verified field changes and, if enabled, up to 20 advisory revisions independently; sample all when fewer exist. Use reproducible random selection and record population, seed and inclusion probabilities. Preserve subject/project breakdowns. Never pool mechanically checkable fields with advisory meaning into one quality rate. Incident cases and correction/undo reports are separate evidence streams. Owner labels and semantic sample review are optional during operation; lack of labels neither counts as success nor pauses availability. Independent human grading remains required for pre-release experiments where the rubric needs it; evaluation labor is not a recurring product workflow.

For verified fields, grade the exact source predicate. For advisory lessons, separately grade anchor/origin compliance, semantic plausibility/support, applicability, useful reuse and harmful reuse. Lack of machine-verifiable meaning is expected and is not by itself an error in this lane; a fabricated rationale, known contradiction or misuse is. Automated source checks cannot mark advisory meaning correct. Use `indeterminate` when the independent rubric cannot decide. Report confirmed errors/adjudicated items, indeterminate and unreviewed counts, uncertainty and reviewer time by lane. A self-selected owner-reviewed subset is not an unbiased error estimate. Delivery is not evidence of use, and zero corrections is not evidence of correctness.

**Unattended advisory operation.** No review timestamp or owner engagement event grants or renews availability. Activation requires the frozen product/safety experiment and one standing configuration choice; eligible items then publish and remain deliverable under their checks without item approval. Automated provenance, scope, anchor, expiry and known-invalidation checks continue. `semantic_status=unverified` remains explicit; unreviewed meaning and zero corrections never become a claim of correctness.

**Automated control health.** Run independently expected deterministic source/provenance/lifecycle regression fixtures and a non-publishing control canary at activation, after relevant code/policy changes and at least daily. A failed fixture pauses its affected class immediately. If required control evidence is more than 24 hours old, pause affected advisory publication and automatic delivery until the checks run successfully; this is an automated operational dependency, not human review. Keep test poison isolated from live memory. Every serving route checks current pause/policy/expiry state. These checks test implemented controls and planted cases, not the truth of arbitrary prose. Frozen model-consuming poisoning regressions run for generator/prompt/consumer-profile changes before rollout; model judgments remain diagnostic.

**Absence and uncertainty.** During owner absence, otherwise eligible advisory items stay available until expiry, invalidation or an operational/incident pause. New eligible evidence may automatically create revisions under the same rules; no review event extends lifetime or clears another pause. Record unreviewed semantic populations, observed useful/harmful reuse, unknown applicability, pause causes and recovery cost. Optional human feedback feeds incident handling. If long-horizon tests show unacceptable semantic errors that only recurring human review can control, the unattended product fails; do not hide that dependency in maintenance. A seven-day soak plus accelerated clock tests cannot certify weeks of semantic accuracy.

**Breaker semantics.** One confirmed severe scope, secret-disclosure, authority or injection error pauses the affected lane/class immediately. Retain two confirmed moderate errors among the latest 20 adjudicated items **within the same lane/class** as a conservative operational pause, with sample age visible; fewer than 20 trigger investigation status and the incident rule below. This is not a statistical test certifying a 2% error rate. For 20 independent checks, `P(X≥2)=1−(1−p)^20−20p(1−p)^19`: 5.99% when p=2%, and 60.83% when p=10%. These are per-window probabilities, not guaranteed weekly false-alarm/detection rates; rolling windows, selected adjudication and correlated fields change them. Twenty clean independent checks still give a one-sided 95% upper bound of about 13.9%.

**Independent correction/undo trigger.** Deduplicate by originating automatic revision and incident. One evidence-backed moderate correction or undo opens an investigation; two distinct confirmed moderate incidents in the same lane/class within seven days pause that scope, regardless of the random-sample count. Exclude owner preference edits, valid source evolution, retries and multiple derivatives of one incident. Show raw counts, reasons, unique published revisions and observed deliveries; do not label this targeted rate an unbiased error rate. Explicit owner correction/undo reasons can feed the trigger without a review queue; model-only suspicions remain diagnostic until corroborated. Freeze these initial operational thresholds before the trial and report pause frequency, missed planted incidents and recovery effort. Tune only through versioned policy. Rejected candidates/verifier failures are tracked separately from published errors.

Quality pauses have a one-hour cooldown, then an automatic recovery attempt using the exact incident regression, the frozen fixture suite and a fresh source-backed canary. ### Build §11. Recovery, retention, deletion and export

**Recovery objective:** RPO ≤5 minutes for acknowledged canonical changes under the measured healthy replication configuration, and an initial restore-time target ≤60 minutes at the declared dataset size. RPO is a loss-window objective, not backup-retention duration. Use continuous SQLite WAL-aware replication to separately permissioned object storage, with a pinned tool such as Litestream evaluated in the spike [R8]. This is asynchronous: a local commit acknowledgement is not remote backup acknowledgement.

Track the last confirmed remote recoverable sequence and the age of the oldest acknowledged commit not yet protected by it, not merely uploader activity. Lag is zero when all commits are protected, even if the last write was long ago. Warn at two minutes; after five minutes mark RPO protection breached and pause new automatic publication until caught up. Local capture/working commits may continue within capacity, explicitly marked not yet remotely protected. A simultaneous volume loss during that interval can exceed the objective; neither a flag nor a paused writer retroactively makes asynchronous replication synchronous. Report observed loss during destruction/restore drills. A stronger hard acknowledgement guarantee would require remote durability in the acknowledgement contract and a different availability tradeoff.

Retain encrypted content-bearing snapshots/replication segments for at most 30 days by default. Test the tool's compaction, object versions and garbage-collection retention; set lifecycle rules accordingly. Replication is part of the deletion inventory, not an exemption. Replicated audit/data is not an independent integrity authority merely because it is another copy. Protect secret-store recovery separately; memory export never includes usable secrets.

Logical deletion is immediate at the service control boundary: tombstone target and known transitive derivatives, withdraw affected published fields, deny new reads/dispatches, cancel queued jobs and reject late commits through dependency checks. Repeated ingest/replay cannot recreate deleted identities. Conservative dependency invalidation may remove more derived content than necessary; permitted survivors can be recomputed later. Current restrictions always override historical views and pinned values.

Purge content-bearing source/candidate/revision/audit/job payloads, managed exports, indexes, SQLite free pages/WAL and replication snapshots/segments using tested store-specific procedures. Distinguish active-store purge, backup expiry and external/provider copies. A SQL row deletion is not full physical erasure. Explain limits of encrypted-volume/provider deletion; already delivered independent copies cannot be recalled. Minimal non-content identities, deletion markers and audit envelopes may remain to prevent resurrection; avoid content-bearing hashes/labels in broadly accessible logs.

Keep the latest deletion/revocation ledger outside the database rollback set. Apply live denial locally even if its independent copy is unavailable, but mark restore protection pending and do not claim deletion completion. Restore into an isolated environment, establish that the latest control ledger is available/current, apply it, validate schema/pointers/idempotency, then serve. If current control history cannot be established, do not serve the restored data. Backup data plus a stale control ledger is insufficient. No network write is performed inside a canonical transaction; an outbox reconciles control-copy status with visible incomplete states.

**Installation deletion propagation.** Before production capture, implement these semantics in lite and the gateway. The service owns its capture spool, uploader receipts, provenance/coverage records and managed derived caches on each enrolled installation. Original client transcripts, source repositories and unmanaged exports are outside this automatic purge boundary; identify them as external copies rather than claiming deletion or deleting unrelated user files.

### A3. S1a-lite: the default operational baseline

**Question:** can one owner with one policy get the required automatic-memory benefit from generated cards, private git and minimal durable intake? Budget six to ten focused days for the base, including local delivery and installation control/deletion synchronization, plus two to three for client file-provenance/reconciliation integration if selected (eight to thirteen total), then a seven-day shadow workload. A typed-only trial requires an explicitly reduced product scope. Keep live external actions disabled. Report incomplete when the selected scope exceeds the cap; do not silently implement half the gateway.

Lite has read APIs and two **content-intake** routes: `POST /v1/checkpoints` and `POST /v1/manifests` over HTTPS. It additionally implements Build §11's installation control-feed read and non-content acknowledgment route. A local command hook writes a reduced, scrubbed spool; a supervised uploader synchronizes controls before sending eligible queued bodies. Hook execution does not wait for cloud acknowledgments. No laptop-to-cloud mount or existing authorization server is assumed. Initial MCP is a read-only local stdio adapter over authenticated cloud REST, with a separate read-scoped credential. Hosted remote MCP authorization needs a separate estimate; no bypass is implied. MCP-only clients without a capture integration cannot submit checkpoints.

**Storage boundary.** Git is canonical for card snapshots, pins and publication history. Prefer a small local SQLite database on the service's durable volume for accepted intake, command digests, uniqueness, receipts and processing outbox; a maintained transactional spool is an alternative if measurably simpler. The local installation spool may likewise use SQLite. This is embedded storage, not adoption of the full gateway [R22]. Keep payload retention, purge/WAL handling and backup inventories for every store. Credentials and current denial/control state remain separately protected; a git checkout cannot roll them back.

There is no atomic transaction spanning SQLite and git. Commit intake, uniqueness and receipt before acceptance; an idempotent publisher records a stable generation/run identity and input IDs, writes the card commit, then marks those inputs processed. After a crash between git commit and processing acknowledgment, reconcile by run/commit identity before retry. Check live grants, tombstones and pins before publication and serving, so a late or stale commit is not made visible. Test these boundaries rather than claiming cross-store atomicity or duplicating canonical card authority. Migration imports both card state and intake/control identities.

**Compare credentials before implementing.** The same-user compromised client can use an accessible key or signer under every option. Additional sender binding helps with exported/stolen credentials in other contexts; it does not establish honest reports or complete manifests.

### Expansion §1. S1b: restricted sources and raw crossings

Enable only before heterogeneous policies, employer/client sources or exceptional raw cross-project reads are admitted. Keep residency, model processing and client-read rules distinct. A deployment-hosted model is not a model on the source device. Issued client class is an administrative control, not attestation of a remote model's actual behavior.

Every content-returning route records source/revision/policy exposure durably **before** release. Direct writes, checkpoints, transcripts and later derivatives inherit the conservative conjunction of explicit dependencies and all prior session exposures. Fork/resume/compaction/new client IDs do not reset known restrictions. For ambiguous late ordering, use the stricter known union and bounded quarantine. Content received outside the service is outside this guarantee.

Processing checks cover all inputs and the query on every model/engine call; apply the intersection of source permissions recursively. Mixed-source processing is allowed only when an explicitly eligible processor can handle the conjunction; otherwise quarantine/expire. Stripping injected blocks reduces duplication, not restrictions on paraphrases. Source default policies do not excuse missing provenance or unknown restrictions.

Standing disclosure rules can publish exact qualifying outputs automatically, without exposing raw sources or authorizing later unlisted inputs. An optional owner exact-output exception affects only its named revision/audience/processor; tightening or deletion overrides it. Validate source/policy epochs at scheduling, dispatch and commit. Failed cases never become human review tasks.

### Expansion §2. S2: retrieval and richer lifecycle

Add general search/conflict handling only after card/report retrieval fails on recorded tasks. Before an index, vector system or engine, compare deterministic cards, an agent searching the substantive authorized scrubbed session-summary corpus with a manifest and read-only file tools, a full-context baseline where that same complete corpus fits, and the proposed retrieval method on the same frozen workload and approved lanes [Q4]. Use identical source permissions and total token/time budgets, count all file/tool calls and latency, and include stale/conflicting/irrelevant memory. Retain agent-over-files if it meets the need. Each method receives only the caller-authorized, origin-labelled corpus; any raw-history expansion beyond S1a must first earn its access contract. The export contains only that permitted corpus; a filesystem sandbox is not permission to expose raw cross-project working memory. Seed subjects with cardinality `one` or `many`; no noun-phrase guessing. Use source-specific authority/transition rules, separate weaker challenges from coequal conflicts, and pack a whole visible conflict group or a marker rather than a selected winner.

Choose the authorized corpus before scoring. Shared FTS5 BM25 statistics can reflect inaccessible documents even after row filtering; use authorized-corpus statistics or an index matching exactly that corpus. Do not truncate by a global score first. Lower FTS5 BM25 is better; handle ties/all-equal scores explicitly. Hidden additions must not affect exposed counts, scores or ordering in the owned path [R10]. Timing side-channel elimination is not promised.

`known_at` and full bitemporal queries are **deferred even within S2** until a concrete historical-debugging need earns them. Preserve ordinary revision/audit order now. If enabled, filter records and supersession edges by recorded activation time before valid-time evaluation; candidate time is not activation time. Redacted superseders retain non-content edges so older text does not revive. Branches form contested groups; present-day read denial always applies. Exact valid time determines currency, while ranking buckets affect freshness/order only.

### Expansion §3. S3: production capture breadth

Active-session narrative sharing is deferred beyond the initial post-closure contract. It needs independently attributable checkpoint boundaries, tested input coverage and late-taint invalidation without session-ID resets. Measure discovery-to-availability against concurrent-agent tasks before adding it. A promising A2.3 result likewise requires a separate lower-trust production contract and release evidence; neither expansion is enabled by this heading.

Extend the narrow source mapping already proven in S0b/S1a to more source formats and transcript adapters. If S0b-2 earned the advisory lane, extend source-linked episode context alongside claims and applicable lessons [Q1, Q2]; broader input provenance still requires its own gate. Keep intended plans distinct from completed outcomes. Compare this representation with the simpler baseline before adding consolidation machinery. Compare reusable extraction first; do not presume bespoke distillation. Pin adapters and test actual client/subagent/session/checkpoint formats rather than assuming hooks are identical or all sessions end cleanly. Register sessions early, checkpoint during operation where supported, recover only grant-checked unambiguous logs, and show unsupported-source coverage gaps.

Measure durable-item precision/recall and false no-memory outcomes, not only sessions that produced something. Known/received/processed/applied/card-refreshed/no-memory/failure states have explicit denominators and terminal expiry. A session with ten target facts and one captured has low recall even if marked applied. Initial diagnostic goals: ≥80% useful-item recall, ≤2% observed unsupported verified-lane publication and ≤10% false no-memory cases, with uncertainty and an appropriate held-out sample; do not claim population accuracy from a small pilot.

Every new source/store/processor extends provenance, policy, audit and deletion tests before use. Preserve explicit source dependencies for every derivative; restrictive inputs also require Expansion §1. Existing lane-specific source/anchor/origin checks remain authoritative; semantic advisory errors are reported separately. Model-generated claims do not gain broader privileges because extraction is automated.

### Expansion §4. S4: background semantic maintenance

Initial automatic extraction, evidence-driven update/withdrawal and deterministic advisory capacity turnover are required by the first product gate and Build §6.1. This expansion adds richer semantic consolidation and learned selection; it does not defer the core automatic upkeep promise.

Evaluate automatic consolidation, links, summaries and retirement by action class. Test outcome-linked reuse feedback [Q2, Q8]: record which memory was delivered, whether its use is actually observed, the task outcome and the provenance of any usefulness judgment. Delivery is not proof of use, and a successful task does not prove which memory caused success. Model judgments are diagnostic signals, never source authority or permission to bypass the selected publication-lane checks. Use a commit-sequence cursor so late-recorded corrections with old source dates are not missed. Model outputs are typed candidates with full input dependencies; field CAS, pins, verification, rate limits, atomic audit and source policy still apply. Leases control duplicate work, not correctness.

Use frozen regression and fresh canary sets, useful-task outcomes, evidence errors, corrections, stale pins and queue cost. Include later-task transfer, negative transfer, valid-update acceptance, weak-source overwrite resistance, obsolete-memory use and selective repair [Q5–Q9]. Adaptive retrieval/consolidation must improve held-out task outcomes without critical scope/authority regressions; compare it with unchanged memory at the same total budget. No Wilson promotion from approval counts; no planted false proposals in live memory. Extend non-blocking audit sampling and scoped breakers, keeping unread or model-disputed outcomes explicit. Enable an action class only if it provides measured value at acceptable error/cost. Models may propose retirement; permanent purge still requires a configured rule or owner command.

### Expansion §5. S5: optional engine adapter

EverOS, mem0 and other engines remain candidates for a measured retrieval/maintenance gap. Extraction reuse can happen earlier without adopting an engine as canonical storage. Evaluate a pinned release/commit and exact required behavior, including source mapping, provider control, custom metadata, namespace isolation, revision/deletion/rebuild behavior and cost. Authentication through the gateway may be sufficient; a missing native feature is not automatically a rejection if a small wrapper meets the actual contract.

Compare engines with the S2 agent-over-files baseline at the same allowed corpus and total cost. Engines never write canonical memory directly or render startup briefs. Every result maps back to authorized gateway IDs/revisions and current publication/deletion rules. Drop unmappable results. Keep full project namespaces separate from published-only namespaces; an engine cannot ingest a source its processor is not allowed to receive. Cross-source reranking requires permitted combined input, not an implicit provider call. Explicitly label `deep`→`fast` fallback and test that it does not relax policy.

Disable unwanted autonomous rewrites where supported; otherwise isolate and treat all outputs as candidates. A fork requires a concrete unfixable adapter gap plus a maintenance budget. LoCoMo-style research benchmarks are optional comparison evidence, not product acceptance or proof that this owner's handoffs improve.

### Expansion §6. S6 and parked features

Add connectors individually when their capabilities and costs are justified. Entity cards, graph experiments, portfolio scoring and cross-device breadth beyond the initial handoff test remain parked. If portfolio scoring is earned, use only disclosed published data; bounded overdue features must never depend on hidden activity. Offline replay remains disabled unless a need justifies per-client/project isolation, all-source permissions, credential/TTL expiry and honest delayed revocation. No system can recall content already delivered to a disconnected device.

Task coordination and external-system actions require separate product contracts. Memory can help agents remember; it does not allocate work, enforce repository locks or authorize emails, merges or source deletions.

## Appendix F. Research basis and implementation commitments

### Research §1. How this research is used

The research review checks primary-source passages supporting the retained summaries for Q1–Q9 and the origin-laundering mechanism and scope limits in Q10. It is targeted claim verification, not a full methodological audit or exhaustive literature review. Versioned links identify the readings, and publisher/ACL records support venue labels. Reported results have not been reproduced for this project; component and product validation remain separate gates.

Separate three types of evidence: a paper supports a hypothesis or method; a pinned component test establishes available behavior; our own held-out tasks establish product value. None substitutes for another. Results across different models, datasets, prompts and budgets are not a vendor ranking. The studies do not establish this service's publication safety, authorization, storage durability or audit completeness. Those remain engineering contracts tested independently.

**Adopt** below means include the design/test requirement in the roadmap. **Probe** means a bounded experiment, not production approval. **Defer** means no implementation commitment until the named stage earns it. Keep all performance numbers as external findings, not promised service gains; no paper's headline percentage becomes our acceptance threshold.

### Research §2. Selected readings, findings and limits

**[Q1] EverMemOS: A Self-Organizing Memory Operating System for Structured Long-Horizon Reasoning.** [Reading: arXiv v2](https://arxiv.org/html/2601.02163v2); [ACL 2026 publication](https://aclanthology.org/2026.acl-long.2125/).

The method separates episodic records, atomic facts and time-bounded prospective information, then consolidates and retrieves structured context. This informs our distinction between an observation, a claim and an intended plan. **Probe:** an EverMind extractor with preserved source mappings in S0b-2; consider consolidation in S3–S4 and richer retrieval in S5. **Limit:** conversational benchmark findings do not establish verified sharing or production governance. The paper's EverMemOS architecture and the currently documented EverOS package are distinct evaluation artifacts; pin and test the actual component before adopting it.

**[Q2] Remember Me, Refine Me: A Dynamic Procedural Memory Framework for Experience-Driven Agent Evolution (ReMe).** [Reading: arXiv v2](https://arxiv.org/html/2512.10696v2); [Findings of ACL 2026](https://aclanthology.org/2026.findings-acl.829/).

ReMe extracts contextual procedural experience, retrieves it for related tasks and refines its use with outcome feedback. Its experiments also caution against indiscriminately accumulating failure-derived lessons. **Probe:** preserve conditions, attempts, outcomes and evidence privately; test the bounded advisory representation and later-task usefulness in S0b-2. **Defer:** adaptive experience refinement to S4. **Limit:** tool-use benchmark gains do not prove that an agent's explanation is causal or universally reusable. Our lesson fields and publication restrictions are adaptations, not a reproduction of ReMe or an adoption of model confidence as truth.

**[Q3] Mem0: Building Production-Ready AI Agents with Scalable Long-Term Memory.** [Reading: arXiv v1](https://arxiv.org/html/2504.19413v1); [publisher record: ECAI 2025 proceedings, DOI 10.3233/FAIA251160](https://journals.sagepub.com/doi/10.3233/FAIA251160). The cited publisher record identifies the ECAI proceedings edition.

Mem0 evaluates extraction, update and retrieval against alternatives including full conversational context, reporting efficiency benefits on LoCoMo. **Adopt:** require a full-context diagnostic: Table 2 reports Overall J 72.90 for full context versus 66.88 for Mem0 on LoCoMo, with materially greater full-context input/latency. Measure total task cost alongside quality, including preparation and maintenance; neither method is presumed best locally. **Probe:** mem0 as an alternate extractor if the initial candidate is unsuitable within the same budget. **Limit:** conversational QA and reported cost accounting do not predict our coding/handoff outcomes. Model-suggested add/update/delete decisions remain candidates behind our gateway; neither the graph variant nor vendor-reported savings is assumed necessary or transferable.

**[Q4] LongMemEval-V2: Evaluating Long-Term Agent Memory Toward Experienced Colleagues.** [Reading: arXiv v1](https://arxiv.org/html/2605.12493v1), preprint.

The evaluation covers static/dynamic state, workflows, gotchas and mistaken premises. It reports 72.5% average accuracy for AgentRunbook-C, 48.5% for the strongest non-AgentRunbook RAG baseline and 69.3% for the off-the-shelf coding agent. Table 2 gives the latter 177.2/185.8 seconds on Small/Medium (mean 181.5 seconds); AgentRunbook-C uses 108.3/139.9 seconds. The coding agent searches trajectory files with a workflow, manifest and helpers. **Adopt:** task tags plus an agent-over-authorized-Markdown diagnostic in S0 and a required S2 comparison. **Limit:** different controllers and offline web-history context gathering prevent treating the headline as a general architecture ranking or a forecast for coding handoffs. Count latency and all tool/model costs locally.

**[Q5] EvoMemBench: Benchmarking Agent Memory from a Self-Evolving Perspective.** [Reading: arXiv v2](https://arxiv.org/html/2605.18421v2), preprint.

The study distinguishes within-episode memory from transfer across episodes. It finds competitive long-context baselines and cases where memory adds little or harms performance. **Adopt:** keep simpler baselines, test irrelevant memory and measure negative transfer. **Defer:** a production adaptive reuse policy until S4 demonstrates a benefit on held-out follow-on tasks. **Limit:** benchmark-specific transfer results do not establish a universally best memory architecture. Retention, revision and successful reuse need separate evidence.

**[Q6] From Recall to Forgetting: Benchmarking Long-Term Memory for Personalized Agents (Memora).** [Reading: Findings of ACL 2026 paper](https://aclanthology.org/2026.findings-acl.1337.pdf); [publication record](https://aclanthology.org/2026.findings-acl.1337/).

Memora stresses updates across longer interaction histories. Its FAMA metric explicitly penalizes obsolete-memory use, which a presence-only score can miss. **Adopt:** report current-fact correctness and invalidated-memory reuse separately after updates/deletion. **Limit:** controlled personalized-conversation tasks and partially model-judged scores do not certify our publication gate. Our local stale-use measure is inspired by this concern, not an implementation of FAMA or a comparable published score. Deleting stored data and preventing obsolete answers are related but distinct tests.

**[Q7] Probing Stability–Plasticity Tradeoffs in Agent Memory through Cognitive Experimental Paradigms (MemProbe).** [Reading: arXiv v1](https://arxiv.org/html/2609.30558v1); [EMNLP 2026 publication](https://aclanthology.org/2026.emnlp-main.2473/).

MemProbe tests legitimate updates, misleading contradictions, reinforced memories and recall-triggered changes. **Adopt:** paired chronological fixtures in which a valid source update must take effect but a weaker later claim must not overwrite supported state. **Limit:** the compact diagnostic suite and controlled reader are not exhaustive production evidence. We borrow its controlled comparisons, not a biological claim about model memory. Repeated copies of the same source still do not count as independent support.

**[Q8] TAME: A Trustworthy Test-Time Evolution of Agent Memory with Systematic Benchmarking.** [Reading: arXiv v2](https://arxiv.org/html/2602.03224v2); [EMNLP 2026 publication](https://aclanthology.org/2026.emnlp-main.2100/).

TAME studies degradation of trustworthiness during otherwise benign memory evolution and proposes an executor/evaluator feedback loop. **Adopt:** evaluate useful and harmful reuse separately. **Defer:** outcome-linked reuse weighting to S4, with regression and canary checks. **Limit:** an evaluator's attribution of success or harm can be wrong; a second model is not independent ground truth. We will not use its agreement or utility score as source verification, publication permission or authority to remove an owner pin.

**[Q9] MemSecBench: Tracking Agent Memory Poisoning from Persistence to Consequence and Repair.** [Reading: arXiv v1](https://arxiv.org/html/2607.27080v1), preprint.

The benchmark follows persistence, exposure, adoption, consequences and repair. Across its 24 configurations it reports 84.2% malicious-memory persistence and 50.3% full write–execute success; its abstract reports 56.1% selective repair among successfully poisoned cases. Removing the targeted poison and preserving benign memory are separate requirements. **Adopt:** deterministic lifecycle/repair fixtures in S0b-1, model-consuming cases in S0b-2, and REL-08/REL-16 regressions. **Limit:** these benchmark averages are not our threat prevalence or predicted error rate. External actions are mocked in our probe; a clean published field does not demonstrate repair if harmful content survives in working memory or derivatives.

**[Q10] Securing LLM-Agent Long-Term Memory Against Poisoning: Non-Malleable, Origin-Bound Authority with Machine-Checked Guarantees.** [Reading: arXiv v1](https://arxiv.org/html/2606.24322v1), preprint.

The study describes laundering through agent summaries, trusted-tool echo and manufactured corroboration. **Adopt:** REL-07/REL-08 preserve untrusted origin through tool output and restatement; Build §4.1 adds conservative session/file provenance and capture reconciliation. **Limit:** the paper's formal protection concerns consequential actions using untrusted-origin values. Section II says non-consequential answer bias is mitigated rather than eliminated; §VII's related-work discussion explicitly places reflection-induced answer bias outside scope. Advisory text and working briefs directly influence answers, so that limitation matters here. Our hook manifest is client-attested rather than the paper's trusted enforcement boundary, and we neither implement its construction nor inherit its guarantees. Unknown origins remain ineligible; even eligible origin does not establish semantic truth or freedom from answer bias. Our file ledger and transcript reconciliation improve bounded implementation coverage while retaining the stated client-attestation trust limit.
